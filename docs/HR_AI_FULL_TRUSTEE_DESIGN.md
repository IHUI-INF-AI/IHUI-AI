# 人事板块 · AI 深度融合与全流程托管方案设计

> 状态：设计稿（待评审，未动代码）
> 日期：2026-11-12
> 关联：`docs/HR_SYSTEM_COMPLETE.md` 第十一章「AI 对话接入」——本文是其从「接入」到「托管」的演进设计
> 目标读者：人事产品负责人 / AI 平台架构师

---

## 0. 一句话主张

**不要「传统 SaaS + AI 按钮」，要做「AI Agent 托管中枢」**：
人不再驱动每一步、调每一个接口；人只说目标（"我要请三天假""补昨天的缺勤""给老板出上月报告"），
**HR Agent 编排多个工具、自评结果、主动补救**，人只在真正需要判断的异常决策点介入。

| 维度 | 传统思维（现状） | 深度融合（目标） |
|---|---|---|
| 触发 | 人问一句，AI 答一句（被动） | AI 主动巡检、主动推送（托管） |
| 粒度 | 单工具 = 单 API 映射 | 目标级 = 多工具编排闭环 |
| 人的角色 | 驱动每一步 | 只确认异常决策 |
| 判断 | 人判断下一步 | Agent 自评 + 补救，判断类才升人 |
| 记忆 | 无（每次从零） | 有（员工上下文、历史决策、偏好） |

## 1. 现状诊断（基于实读代码）

### 1.1 三条 AI 通道（必须分清，否则方案会做错）

| 通道 | 机制 | hr 覆盖 | 用途 |
|---|---|---|---|
| **产品端 AI 对话** | `api_tools_bridge.py`：拉 OpenAPI spec **自动**生成 `api_` 前缀工具 | **26/26 全覆盖**（本次 `buildSchema` 修复后） | 每个终端用户经对话调用 |
| **CLI 开发者端** | `hr.json` 清单 → `gen-ai-tools-from-routes.mjs` → `hr.ts` 手写工具族 | `hr.ts` 26 / `hr.json` **仅 16**（不同步） | 服务开发者 agent |
| **领域 Skill** | `ai-service/app/skills/` | **无 HR skill** | 现有 content_engine / koubo_workflow |

**关键纠正**：产品端工具面无缺口——`buildSchema` 已让 26 端点全量对 AI 可见。
`hr.json` 的 16/26 是 **CLI 侧维护债**，与产品端无关（两套独立通道）。

### 1.2 真正的缺口：不是"看不见"，是"只会裸调"

产品端 26 端点虽可见，但 AI 现在只会**把 HTTP 接口逐个翻译给 LLM**：
- 员工说"我发烧了请假"→ AI 只能调 `hr_leave_create`，然后**停在那里等人操作**；
- 多步流程（查额度→匹配审批规则→落实例→通知→跟踪超时）**没有 agent 串起来**；
- 定时巡检、主动推送**没有 HR 场景落地**；
- 判定类与决策类动作**没有区分自动化边界**。

结论：缺的不是接口，是**人事领域的 Agent 编排层**。

## 2. 目标架构：四步改造

```
┌─────────────────────────────────────────────────────────────────┐
│                     HR AI 托管中枢（新增）                        │
│                                                                  │
│   ① 目标解析 → ② 多工具编排 → ③ 自评/补救 → ④ 异常升人          │
│        │              │              │             │             │
│   HR Agent Skill   26 hr_* 工具   goal-loop 迭代  human-in-loop   │
│  (领域编排范式)   (api_tools_bridge) (goal-loop.ts)  (决策点)     │
└─────────────────────────────────────────────────────────────────┘
         │                              ▲
         │ 编排                          │ 主动触发
         ▼                              │
   api_tools_bridge                automation_tools
  (26 端点原子能力)              (agent 建定时任务)
         │                              │
         ▼                              ▼
   apps/api hr 路由  ──── cron ────  主动巡检/推送
   (判定内核 attendance-core 单源)
```

### 四步改造

**① 补齐编排原子能力**（不是补接口可见性，是补"领域原子动作"）
- 产品端 26 端点已可见，无需补注册。
- 需补的是 **AI 友好的复合查询**：如"某员工本月出勤画像"（现在要 AI 自己拼 records+stats+leave 三次调用）。
- 落点：`ai-service` 新增 HR 查询聚合工具，或直接在 Agent Skill 内编排。

**② 建 HR Agent Skill（核心）**
- 落点：`apps/ai-service/app/skills/hr_workflow/`，仿 `koubo_workflow` 范式。
- 把"目标级流程"写进 skill 指令：教 agent 遇到"请假""补缺勤""出报告"时按固定编排链调用工具、何时自评、何时升人。
- 详见第 3 节。

**③ 被动问答 → 主动托管**
- 用现有 `automation_tools.py`（agent 可在对话里建 `user_automations` 定时任务）。
- HR 场景：让 agent 主动建"每日 09:00 巡检昨日异常并 @ 管理员""每月 1 日出生勤报告"。
- 执行侧复用 `automations/orchestrator.ts` 的多步流水线 + 韧性（transient 失败回队、permanent 终态、全链审计）。

**④ 异常才找人（human-in-the-loop 只在刀刃）**
- **纯算法全自动**：迟到/早退/缺勤判定（`attendance-core` 单源）、日结、统计、额度查询。
- **AI 建议 + 人确认**：补卡审批、多级请假审批决策——agent 先给"建议通过/驳回 + 证据"，人一键确认或改判。
- 边界原则：**涉及他人权益的判断性动作，AI 不自动落锤，只备好决策包**。

## 3. HR Agent Skill 编排设计

落点：`apps/ai-service/app/skills/hr_workflow/`
（目录：`SKILL.md` 编排指令 + `tools.py` 领域聚合工具 + `flows/` 各场景编排流）

### 3.1 场景 A：员工请假（端到端托管）

员工："我明天想请三天事假，家里有事。"

```
Agent 编排链：
1. 识别员工身份 (__user_id，宿主注入，LLM 不可控)
2. hr_leave_balance(employeeId, year)         → 查事假余额是否够 3 天
3. hr_attendance_rule(departmentId)           → 确认工作日，算实际占用天数
4. 匹配审批规则：hr_approval_flows() 过滤 leaveType=事假 ∧ 3天∈[minDays,maxDays)
5. hr_leave_create(...)                       → 建请假单
6. hr_approval_submit(leaveId)                → 落多级审批实例 + 通知一级审批人(微信)
7. 回员工："已提交，审批链=张三→李四，预计48h内完成，超时会自动升级，我盯着进度，有结果通知你"
8. 【托管】登记一个审批进度跟踪(automation)：状态变更时主动推送员工
```

**自评点**：步骤 2 余额不足 → agent 不硬提交，改为"你的事假余额仅剩 1 天，3 天需走[无薪事假/调休]分支，要我按无薪继续吗？"（升人确认）。
**人介入点**：仅审批决策环节（审批人确认）+ 余额不足的分支选择。

### 3.2 场景 B：补昨日缺勤（管理端托管）

管理员："昨天谁没打卡？能补的帮我补了。"

```
Agent 编排链：
1. hr_attendance_backfill({backfillDays:1})   → 跑缺勤补录，拿到昨日缺勤名单
2. hr_attendance_records(departmentId, date=昨日) → 拉明细，区分"真缺勤"vs"漏卡"
3. 对每条漏卡：查是否有对应补卡申请 hr_punch_fix_list
4. 无申请的 → agent 汇总名单 + 建议："这 3 人漏卡(有定位/无申请)，要我代提补卡申请还是先通知本人？"
5. 有申请待审的 → agent 给决策包："王某漏卡有补卡申请+事由'地铁故障'，建议通过；李某无合理事由，建议驳回"
```

**人介入点**：步骤 4/5 是判断类——agent 只备好建议+证据，一键批量确认或逐条改判。
**全自动部分**：步骤 1-3 的扫描与分类（纯算法）。

---
### 3.3 场景 C：月度报告主动推送（无人触发）

```
自动化(经 automation_tools 建，cron 每月 1 日 09:00)：
1. hr_job_run('monthlyStats', date=上月末)   → 汇总上月各部门考勤
2. hr_attendance_stats(departmentId, 区间)   → 分部门统计
3. hr_leave_list(区间) + hr_daily(月份)      → 请假/异常明细
4. Agent 综合成一份"上月人事健康报告"：出勤率、异常 TOP、请假趋势、风险点
5. 主动推给管理员(站内信 + 微信)，附"要不要我深挖某部门？"
```

**这是"托管"的本质**：没人问，AI 到点自己做、主动给结论。

## 4. 安全与权限边界（全流程托管的红线）

托管不等于放权，三条硬边界：

1. **身份链路不变**：所有编排仍走 `__user_id`（宿主注入、LLM 不可控）+ 路由 RBAC
   (`hr:attendance:view`/`manage`)。Agent 再聪明也越不了权——它只能编排身份允许的工具。

2. **写操作分级**：
   - 建档/规则/提交申请 → 身份够即可（agent 可自动）
   - 审批决策/补卡回写 → agent 只备决策包，**人确认后落锤**（不自动）

3. **审计全留痕**：编排每一步走现有审计通道；判定用 `attendance-core` 单源，
   agent 不复制判据（与教育端同纪律）。自动化执行复用 `orchestrator.ts` 的
   redact + 审计（PAT/凭据绝不落日志）。

## 5. 分阶段里程碑

| 阶段 | 内容 | 验收标准 | 依赖 |
|---|---|---|---|
| **P0 收口 CLI 清单** | `hr.json` 补 10 条(daily/approval) → 重跑生成器同步 hr.ts 26 | 生成器幂等，hr.ts 与 hr.json 一致；CLI agent 全 26 工具可调 | 无（纯维护债） |
| **P1 HR Agent Skill** | 建 `hr_workflow` skill；跑通场景 A(请假)、B(补缺勤) | 两个场景端到端对话跑通，含自评点与人介入点；不破坏 401/403 | P0；现有 26 工具 |
| **P2 主动托管** | 经 automation_tools 落地场景 C；agent 主动建巡检/报告自动化 | 无触发下 agent 到点主动推送月报/异常提醒；失败韧性走 orchestrator | P1；automations 基建 |
| **P3 智能决策** | 决策包(建议+证据)规模化；跨月趋势预测、排班建议 | 管理端"一键确认"覆盖 80% 常规审批；预测类准确率有评测 | P2；历史数据 |

**工作量性质**：P0 是小时级维护；P1/P2 是天级（skill 编排 + 联调）；P3 是周级（需评测集）。
精确工期待评审后按排期估。

## 6. 待评审决策点

1. **复合查询工具归属**：放 `ai-service` HR 聚合工具，还是 Agent Skill 内多步编排？（倾向后者，少一层 API）
2. **写操作自动化边界**：审批决策是否允许"低风险全额自动、高风险才确认"？还是一律人确认？（倾向一律人确认起步）
3. **P1 优先场景**：先做员工侧(请假)还是管理侧(补缺勤)？（倾向员工侧，覆盖面广）
4. **hr.json 同步机制**：把 `hr.json` 补全一次性收口，还是顺手让生成器也从 OpenAPI spec 派生避免再漂移？
