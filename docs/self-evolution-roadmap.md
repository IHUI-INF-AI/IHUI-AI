## 2. 自进化飞轮模型（闭环各环节）

```
① 感知发现  → ② 自治决策  → ③ 编码实现  → ④ 守门验证
     ↑                                              ↓
⑥ 经验沉淀 ← ⑤ 部署发布  ← ⑦ 验证回滚  ← ⑧ 效果度量
```

- ① **感知发现**：从错误日志、监控告警、用户反馈、使用数据中自动提炼可执行改进项并立项。
- ② **自治决策**：基于收益/风险/成本模型自动排期，决定"做什么、做不做、做到什么程度"。
- ③ **编码实现**：多 agent 并行编码，受认领租约与对象空间 CAS 约束，不污染他人在途。
- ④ **守门验证**：现有 `guardian` 全量门 + 自动补全的 E2E 测试。
- ⑤ **部署发布**：现有 `IHUI-DEPLOYLOOP` 推进，叠加金丝雀分流。
- ⑥ **经验沉淀**：每次改动/事故后自动提炼教训写回 `AGENTS.md` / memory。
- ⑦ **验证回滚**：部署后自动比对线上指标，异常自动回滚到上一可运行态。
- ⑧ **效果度量**：量化"改了之后是否真的变好"，反馈回 ② 调参。

**三道保险（横切所有环节）**：不可变护栏（锁死守门与核心约定）、成本熔断（预算上限）、人工阀（AI 不可自决清单 → 安全停机等人）。

## 3. 缺口详述与落地（P0–P4）

### P0 — 安全护栏（无人化先决，必须最先做）

- **不可变护栏**：在 `guardian` 之上建一层 AI 改不动的"根护栏"——用独立的、只读校验和（hash 清单）保护 `scripts/guardian-runner.mjs`、`AGENTS.md` 铁律段、`judgement-libs.json` 等核心文件；任何对这些文件的改动必须先通过人工显式解锁，否则部署环 fail-closed 拒绝推进。参考现有 `object-space-land` 的 CAS 思路，但扩展到"规则自身"。
- **成本熔断**：在 `IHUI-DEPLOYLOOP` / 自动 agent 调度层设预算上限（API 调用额、算力时长、部署频次）；超限即停转并告警，避免无人时无限烧钱。
- **影响面隔离与原子回滚**：单 agent 改动限定在独立 worktree/分支；提供一键原子回退到上一个通过守门的可运行态（基于现有 gitdir + 部署环的 ff 结构）。
- **人工阀清单**：明确"AI 可自决范围"与"必须停机等人"的清单（换 API key、控制台操作、真机扫码、对外发布口径等），设计为"安全停机等人工"而非"硬失败"。

### P1 — 感知与闭环

- **需求/异常自动发现器**：消费 `api_logs`、Grafana 告警、用户反馈入口，由 agent 自动聚类 → 生成"可派单改进项"写入台账（复用 `plan-tasks` 入口，带新鲜日期交代）。
- **端到端反馈闭环**：打通 `监控异常 → 自动建单/派单 → agent 修复 → 过门 → 部署 → 部署后指标比对 → 异常自动回滚`。

### P2 — 验证与决策

- **E2E 自动补测**：随代码演进由 AI 自动补全集成/E2E 测试，新模块必须有对应测试才准入（守门扩展）。
- **金丝雀发布**：`IHUI-DEPLOYLOOP` 增加灰度分流 + 部署后自动比对错误率/延迟，异常自动回滚。
- **自治决策模型**：建立收益/风险/成本评估模型，让 AI 自己排期，而非"做什么"永远源于人。

### P3 — 知识自举

- **经验自动提炼**：每次改动/事故后 AI 自动把教训写回 `AGENTS.md` / memory（受 P0 不可变护栏约束非铁律段）。
- **守门规则自生长**：新模块自动生成对应守门项（在单一真源 `judgement-libs.json` 内扩展），但须经 P0 护栏与人工抽检。

### P4 — 治理

- **可审计决策链**：无人状态下"为什么这么改"的决策理由留痕可追责（commit 之外补决策记录）。
- **安全停机而非硬失败**：异常时进入受控停机态并通知人工，而非放任失败扩散。

## 4. 现实约束（必须正视）

- **外部动作面**：换 key、控制台、真机扫码等卡在机主手里，永远需要人工阀，设计目标是"安全停机等人"，不是强行全自动化。
- **网络通道**：GitHub egress 不稳会打断取源/推送；自进化需固化一条稳定推送通路（已用 `schannel` + token 绕过，需固化）。
- **法则底线**：即使全自动化，`AGENTS.md` 的"恒红门禁令""判据单一真源""文档不许写跑不通的出路"等铁律必须保留，且受 P0 不可变护栏保护。

## 5. 落地顺序

```
P0 安全护栏（不可变护栏 + 成本熔断 + 人工阀）  →  能不能放手的开关
P1 感知发现 + 反馈闭环                        →  让进化有源头、有去处
P2 验证回滚 + 自治决策                        →  让进化可信、可排序
P3 知识自举                                  →  让进化越跑越快
P4 可审计治理                                →  让无人状态可控可查
```

## 6. 验收标准（每条可机读）

- P0：根护栏 hash 校验脚本就位，核心文件被改时部署环 fail-closed；成本熔断器在超额时实测停转；人工阀清单文件存在且被调度层读取。
- P1：一次真实线上异常能在无人干预下走完"发现→建单→修复→过门→部署"；异常发现延迟 < 5 分钟。
- P2：新模块缺 E2E 测试时被守门拦下；金丝雀发布异常自动回滚实测成功。
- P3：一次真实事故后 24h 内自动生成经验条目并合入 memory/AGENTS。
- P4：任意一次自动变更可追溯到"决策理由 + 改动 diff + 验证结果"。
