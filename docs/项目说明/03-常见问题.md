## 项目定位

### Q1：IHUI-AI 是什么？

IHUI-AI 是一个**全栈 AI 平台**（TS Monorepo + pnpm workspace + Turborepo），包含 8 端应用（web / api / ai-service / desktop / extension / mobile-rn / miniapp-taro / cli）+ 14 个共享包，提供对话、Agent、RAG、图像/视频/3D 生成、记忆、MCP 工具等完整 AI 能力。

### Q2：IHUI-AI 不是什么？

- ❌ 不是 ChatGPT 套壳（它是平台，不是聊天框）
- ❌ 不是 LangChain 替代品（ai-service 用 LangGraph，但平台本身不卖框架）
- ❌ 不是纯前端项目（后端 + AI 服务 + 多端 + CLI + SDK 全栈）
- ❌ 不是 SaaS 托管服务（开源自部署，`deploy/saas/` 是可选多租户方案）

### Q3：与 ChatGPT / Dify / Coze 的区别？

| 维度 | IHUI-AI | ChatGPT/Claude | Dify | Coze |
|---|---|---|---|---|
| 定位 | 自部署全栈 AI 平台 | 托管聊天产品 | LLMOps 平台 | Bot 搭建平台 |
| 多端 | 8 端 + 5 语言 SDK | 仅 Web/App | Web 为主 | Web 为主 |
| 后端 | Fastify + LangGraph + LiteLLM | 闭源 | Python | 闭源 |
| 开源 | Apache 2.0 | 否 | 开源 | 否 |
| 商业可用 | 是（可商用） | 否（SaaS） | 是 | 否（SaaS） |

### Q4：可以商用吗？

可以。Apache 2.0 协议允许商业使用、修改、分发、私有化部署，只需保留版权声明。注意：不得使用 "IHUI" 商标做背书（除非书面授权）。

## 技术选型

### Q5：为什么 TS + Python 混合？

- **TS** 负责 web / api / cli / desktop / extension / 小程序（前后端 + 多端覆盖广，生态成熟）
- **Python** 负责 ai-service（LangGraph / LiteLLM / 科学计算生态在 Python）
- 两者通过 HTTP API 解耦，各取所长

### Q6：为什么 Fastify 不 Express？

Fastify 性能比 Express 快 2-3 倍，内置 JSON Schema 校验、插件系统、TypeScript 一等支持，且 API 与 Express 相似迁移成本低。

### Q7：为什么 Drizzle 不 Prisma？

Drizzle 是 SQL-first ORM，生成可预测的 SQL，无 N+1 隐藏陷阱，迁移文件可读，包体积小，TypeScript 类型推导强。Prisma 的生成器 + 二进制引擎在 monorepo 中较重。

### Q8：为什么 LangGraph 不 LangChain？

LangGraph 提供显式的状态机 + 图结构编排，可控性强，适合复杂 Agent 工作流；LangChain 抽象层过厚，黑盒难调试。

### Q9：为什么 LiteLLM 不直接调 SDK？

LiteLLM 统一 100+ 模型厂商的调用接口（OpenAI 兼容格式），避免每家 SDK 升级都要改代码，支持负载均衡 / 重试 / fallback。

## 开发与部署

### Q10：最低硬件配置？

| 场景 | CPU | 内存 | 磁盘 |
|---|---|---|---|
| 开发 / 测试 | 2 核 | 4 GB | 20 GB |
| 小规模生产（<100 用户） | 4 核 | 8 GB | 50 GB |
| 中规模（100-1000） | 8 核 | 16 GB | 100 GB |
| 大规模（>1000） | 按需 | 按需 | 按需（K8s + DB 主从 + Redis 集群） |

### Q11：必须用 Docker 吗？

开发环境推荐 Docker（`docker compose up -d db redis`），但本地安装 PostgreSQL 15+ 和 Redis 7+ 也可以。生产环境强烈建议 Docker / K8s 部署。

### Q12：AI 服务无 API key 能运行吗？

可以。LiteLLM 网关无 key 时自动降级 **stub 模式**，返回 mock 响应，便于开发测试。但 stub 模式**不可用于生产**。

### Q13：端口冲突怎么解决？

项目使用 8801-8899 端口段（见 `docs/port-management.md`）。Windows 下可用 `netstat -ano | findstr :8802` 查找占用进程，`taskkill /PID <pid> /F` 终止。

### Q14：Windows 开发有什么注意事项？

- Git 配置 `git config --global core.autocrlf false`（项目强制 LF）
- PowerShell 环境下部分 bash 语法不可用，参考 `scripts/*.ps1` 脚本
- `uv` 安装 Python 依赖比 `pip` 更快更稳
- Docker Desktop 需启用 WSL2 后端

### Q15：如何重置数据库？

```bash
# 停止服务
docker compose down

# 删除数据卷
docker volume rm ihui_ai_pgdata
docker volume rm ihui_ai_redisdata

# 重新启动（会自动重新应用迁移）
docker compose up -d
```

> ⚠️ 会删除所有数据，生产环境请先备份（`deploy/scripts/backup-db.sh`）。

## 认证与安全

### Q16：JWT 过期后怎么续期？

`@ihui/auth` 实现 **token-family 旋转**机制：access token 过期后，客户端用 refresh token 请求新 access token，旧 refresh token 进入黑名单（Redis 存储），防止重放攻击。

### Q17：如何接入微信扫码登录？

在 `apps/api/.env` 中配置：
```
WECHAT_APP_ID=your-app-id
WECHAT_APP_SECRET=your-secret
```
路由在 `src/routes/auth.ts` 中实现 OAuth2 PKCE 流程。

### Q18：生产环境安全检查清单？

- [ ] `JWT_SECRET` ≥ 32 字符（`openssl rand -hex 32` 生成）
- [ ] `CREDENTIALS_ENCRYPTION_KEY` ≥ 32 字符
- [ ] `DB_PASSWORD` / `REDIS_PASSWORD` ≥ 16 字符
- [ ] `CORS_ORIGIN` 设为单域名（如 `https://aizhs.top`）
- [ ] `Grafana` 管理员密码改为强密码
- [ ] 微信支付证书（`cert/` 目录）已配置
- [ ] `.env.production` 未提交到 Git
- [ ] 运行 `grep -E '<your-|<generate-' .env.production` 确认无占位符

详见 [docs/DEPLOYMENT_RUNBOOK.md](../DEPLOYMENT_RUNBOOK.md) §2。

```bash
pip install locust
locust -f scripts/locustfile.py --host=http://localhost:8802
```

性能基线与优化详见 [docs/PERFORMANCE.md](../PERFORMANCE.md)。

### Q20：RAG 检索慢怎么办？

- 确认 pgvector 扩展已启用（`CREATE EXTENSION IF NOT EXISTS vector`）
- 向量表建立 HNSW 索引：`CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)`
- 大批量写入时临时调高 `maintenance_work_mem`

## 贡献

### Q21：如何贡献代码？

1. Fork 仓库，创建 feature 分支
2. 遵循 ESLint + Prettier 规范（`pnpm lint && pnpm format`）
3. 提交前运行测试：`pnpm test`
4. 提交规范遵循 Conventional Commits（`feat:` / `fix:` / `docs:` / `refactor:` 等）
5. 提交 PR，等待 CI 通过 + 守门检查（23 道守门）

详见 [docs/CONTRIBUTING.md](../CONTRIBUTING.md) 和 [CONTRIBUTING.md](../../CONTRIBUTING.md)。

### Q22：提交被 Husky hook 拦截怎么办？

检查 `.husky/pre-commit` 和 `.husky/commit-msg` 脚本，常见原因：
- ESLint 报错未修复
- 提交消息不符合 Conventional Commits 格式
- 测试未通过

可临时跳过（不推荐）：`git commit --no-verify -m "..."`
