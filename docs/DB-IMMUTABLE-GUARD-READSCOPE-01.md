# DB-IMMUTABLE-GUARD-READSCOPE-01 — [IG] 判据面不可变护栏的读取面缺陷

- 状态：已开票（**只记录，不改门**）/ 2026-11-07
- 一句话：`[IG]` 只读「本次提交信息」⇒ 改 gate-body 的人被迫 `--amend` 重写历史；正确读取面应是「本分支自上次推送以来的全部提交信息」，这样豁免可以后补一笔、不必改写已存在的提交。

## 1. 事实

### 1.1 当前读取面的代码位置

| 环节 | 位置 | 行为 |
|---|---|---|
| 取消息 | `scripts/check-immutable-guard.mjs:260-262` `readHeadMessage()` | `git log -1 --format=%B <rev>` —— **只取单枚** |
| 调用 | `scripts/check-immutable-guard.mjs:344-352` | `const message = readHeadMessage(rev)`，`rev` = 被判的那一枚 |
| 判定 | `scripts/check-immutable-guard.mjs:358-362` | `decide({ hits, message, ... })` |
| 推送门注册 | `scripts/guardian-runner.mjs:7290-7296` | `args: ['--range', 'origin/main..HEAD']` —— 逐枚判，每枚都只读自己的消息 |
| 门自述 | `scripts/guardian-runner.mjs:7302` | 原文：「再重写提交信息(会改 sha)」—— 门自己承认出口是改历史 |
| 受保护面清单 | `scripts/data/immutable-guard.json:29-33` | `scripts/check-*.mjs`（`kind: gate-body`） |

`decide()` 的输入里没有任何「段内其它提交」的消息，所以一段里有 N 枚提交时，声明只对「声明所在的那一枚」生效。

### 1.2 被迫 amend 的实例（2026-11-07 本支）

| 阶段 | sha | 差异 |
|---|---|---|
| 原始提交 | `ccac21db76` | 4 个文件（2 枚 gate-body + exempt 台账 + `RELEASE.md`），内容正确、**无声明** |
| push 被拦 | — | `✘ [IG] 判据面不可变护栏 … ⇒ 拦推` |
| 改写后 | `c8ebdfbd0d` | **文件零变化**，只在提交信息里多一行 `immutable-exempt: …` |

同一枚提交的改写前后两端。代码 diff 为空（`git diff ccac21db76 c8ebdfbd0d -- <那 4 个文件>` 全空），变的只有 sha 与提交信息。当日 1 次；只要读取面不改，**每一次改 gate-body 的提交都会重演一次**。

### 1.3 为什么这不是作者失误

门的设计要求「每次改动都在提交信息里显式声明理由」（`scripts/check-immutable-guard.mjs:14-16`）。但该门刻意不进提交链（`scripts/check-immutable-guard.mjs:30-38` 说明了 pre-commit 面结构上没有消息来源，进了就是恒堵门）。于是：
- pre-commit 阶段拿不到声明，
- push 阶段第一次要求声明，
- 而此时提交已经落盘 —— 唯一不跳门、不 force push 的出路就是 `--amend`。

### 1.4 已有的「补声明」通道为什么不够

`scripts/data/immutable-guard-acks.jsonl` 是「已入库未声明提交的事后追认台账」（`scripts/data/immutable-guard.json:41-45`），但它：
- 面向**未推送**即已入库的提交，且本身也是受保护面（改它要声明）；
- 需要逐枚具名 + 到期 + 签名（签名自 `2026-11-11` 起）；
- 与「段内补一笔声明提交」相比，多维护一份台账，且不能解决 push 当场被堵的问题。

## 2. 判据草案：读取面 = 本分支未推段

**目标行为**：豁免声明的覆盖单位从「单枚提交」改为「本分支未推段」。

1. **base 解析**：优先 `@{upstream}` 的 merge-base；无 upstream 时用 `origin/main` 的 merge-base；两者都取不到 ⇒ `exit 2`（未判定），不回落、不记绿（§0.3）。
2. **段**：`base..HEAD` 全部提交。
3. **命中集合**：段内所有提交改动的**并集** ∩ 受保护清单；输出仍逐条点名「哪枚提交改了哪个面」（保留可追溯性）。
4. **声明解析**：拼接段内**所有提交信息**后解析 `immutable-exempt:`；一条合格声明覆盖段内全部命中。
5. **计数**：
   - `declared` = 命中且段内有合格声明；
   - `undeclared` = 命中但段内无合格声明（红）；
   - `declaredIn` = 声明所在 sha（新增输出字段）。
6. **签名**：`signatureRequiredFrom`（2026-11-11）之后，段内任一提交上的有效签名即可覆盖该段。
7. **两面分工**：`--audit-new`（5 分钟巡检）保持逐枚语义不变；只有 `--range`（推送门）改为段语义。
8. **向后兼容**：输出新增 `segmentBase / segmentCommits / declaredIn`；既有 `--json` 字段不删。

## 3. 自指问题：改读取面本身算不算改 gate-body

**算。** `scripts/check-*.mjs` 在清单里（`:29-33`），改 `check-immutable-guard.mjs` 必须声明。

**但不会死锁**：改动与声明可以放在**同一枚提交**里，旧读法下当场就能通过 —— 1.2 节恰恰证明「同枚声明」是可行路径；缺的只是「事后补声明」的自由。因此修复本身不需要任何特批。

**不会追溯判红**：新读法只作用于「未推段」；已入库且未声明的提交继续走 acks 台账。段语义天然满足「不重写已存在提交」的目标。

**实现前需定的三个细节**：
1. base 取 `@{upstream}` 还是 `origin/main`（推荐 upstream 优先，取不到回落 origin/main）；
2. 段为空（例如 rebase 后无新提交）时判绿还是未判定（推荐**未判定**，与 §0.3 一致）；
3. 声明的有效期是否只覆盖「声明提交之后」的命中（推荐**覆盖整段**：段是推送单元，推送是原子动作）。

## 4. 复现与证据

```
# 当日实测
node scripts/check-immutable-guard.mjs --range origin/main..HEAD
#   ccac21db76 时：exit 1（undeclared，命中 scripts/check-*.mjs:2）
#   c8ebdfbd0d 时：exit 0（declared-unsigned；签名要求 2026-11-11 起）
# 代码差异为空
git diff ccac21db76 c8ebdfbd0d -- scripts/check-db-migration-gaps.mjs \
  scripts/migration-hash-drift-exempt.json scripts/check-migration-from-zero.mjs docs/RELEASE.md
```

## 5. 关闭条件

- 推送门在「段内任一提交带合格声明」时判绿，且**不要求改写既有提交**；
- 夹具（3 枚提交：第 1 枚改 gate-body 无声明、第 3 枚纯声明提交）：
  - 段语义 ⇒ 绿；
  - 逐枚语义 ⇒ 红（用同一条历史证明两种读法确有差异）；
- `--audit-new` 逐枚语义不变（回归夹具）；
- 签名策略与 `signatureRequiredFrom` 不改。

## 6. 本票不做什么

- 不改门、不改受保护面清单、不改签名策略、不改 acks 台账；
- 本票只记录缺陷与判据草案，实施另开提交（实施时自身需带 `immutable-exempt:`）。
