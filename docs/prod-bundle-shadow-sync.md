# prod-bundle 运行副本同步(门 104 的修复通道)

`deploy/prod-bundle/` 整目录被 `.gitignore` 忽略,生产服务实际执行的是这份**运行副本**;
仓内的入库源(`deploy/win/*.ps1`、`deploy/scripts/prod-bundle/*` 等)必须与它逐字节相同。

## 两个角色,一条边界

| 角色 | 器物 | 职责 | 写盘 |
| --- | --- | --- | --- |
| 只读闸 | `scripts/check-prod-bundle-shadow.mjs`(门 104) | 逐对判定 sha1 是否全等,接在提交链上 | **从不写盘** |
| 修复通道 | `scripts/sync-prod-bundle-shadow.mjs` | 逐对给出处置,`--apply` 才把入库源覆盖到运行副本 | 仅 `--apply` |

门 104 的判据、阈值、豁免**不得**为了让同步变顺而改动,也不得改成自动写盘 ——
一旦它开始写,提交链上的门就会在自己判红的同时改掉被审对象,判定不再可复核。

登记表的唯一事实源是门 104 导出的 `PAIRS`(实测 23 对脚本类运行副本)。
同步工具直接 `import` 它,不另写一份清单;新增/删除运行副本只改 `PAIRS` 一处。

## 用法

```powershell
# 默认只读(dry-run):逐对打印 已等值 / 待同步 / 拒绝覆盖,并列出将写哪些文件
node scripts/sync-prod-bundle-shadow.mjs

# 显式写盘:先备份、再覆盖、写后逐字节复验
node scripts/sync-prod-bundle-shadow.mjs --apply

# 夹具自检(不碰真实 deploy/prod-bundle/)
node scripts/sync-prod-bundle-shadow.mjs --self-test
```

退出码三态:

| 码 | 含义 |
| --- | --- |
| 0 | 全部登记对逐字节等值,或只剩「运行副本不在本机」的 no-op |
| 1 | 存在待同步(dry-run 档);`--apply` 成功后回到 0 |
| 2 | 拒绝(运行副本有入库源没有的内容)或无法判定(入库源缺失/读取失败) |

## 安全线

- **单向滞后才可覆盖**:运行副本是入库源的子集(少行)时,用入库源整份覆盖。
- **运行副本独有内容 ⇒ 拒绝**:逐条列出独有行并 exit 2,一个文件都不写。
  这是丢内容风险(典型形态:有人在部署机上直接改过运行副本),同步治不了,必须人工先把内容补进入库源。
  整批 fail-closed:任一对拒绝/未判定时,同一轮的其他待同步对也不写 —— 半同步的现场比原状更难判。
- **未登记的运行副本一律不动**:工具只遍历 `PAIRS`,不递归枚举目录,不会碰盲区目录里的其他文件。
- **备份**:写前把旧字节落 `.ihui-agent/backups/prod-bundle-shadow/<YYYYMMDD-HHmmss>/<BUNDLE_REL 内相对路径>`。
  该目录被 `.gitignore` 忽略(`.ihui-agent/*`),运行副本内容不会漏进版本树;工具在写盘前会用
  `git check-ignore` 复核这一点,取不到判定即拒绝写。

## ⚠ 服务影响

`deploy/prod-bundle/` 里的脚本在**服务启动时**读取:

- `--apply` 只改磁盘字节,**不影响正在运行的进程**;要等下一次服务/计划任务重启才生效;
- 本工具**不做**重启、不部署、不推送 —— 重启时机由运维另行决定;
- 也就是说,`--apply` 成功后到服务重启之间,磁盘与线上行为会短暂不一致,这是预期状态,不是新的漂移。

## 边界

- **CI 上不可见**:`deploy/prod-bundle/` 只存在于部署机;在 CI / 干净检出上运行,
  每一对都会是「运行副本不在本机」的 no-op(exit 0),这不等于"已核对"。
- 本工具**不在**提交链与 `check:all` 里:它是人工修复通道,漂移的发现仍由门 104 负责。
- 不覆盖备份轮转/清理;备份只增不减时按 `.ihui-agent/` 既有清理口径处理。
