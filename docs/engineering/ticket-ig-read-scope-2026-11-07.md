# 票：`[IG]` 判据读取面应从「单枚提交信息」改为「本次 push 范围的全部提交信息」

状态：待办（判据面缺陷，非内容错误）
开票：2026-11-07 · `wt-api-defect-mining-1107` 线
关联：`scripts/check-immutable-guard.mjs`（全量档：判 HEAD 与父提交的比对 + **HEAD 提交信息**，见文件头 :23、:48）

## 现象

现行 `[IG]` 全量档只读 `HEAD` 自己的提交信息（`git log -1 --format=%B HEAD`，:261）。
后果：某笔提交已经在仓里、但推送时才被判定「未声明」时，唯一合法出路是把声明补进**那枚已存在的提交**，
只能 `git commit --amend` / `reset --soft` 重写 ⇒ sha 变更 ⇒ 旧 sha 必须打 `lost-commit/superseded-*` 并进 superseded 台账。
本线一天内因此重写了 4 枚（`feff2b9f82`、`65ee36cac2`、`099d96d169`、`062faf69c0`），全部是「内容无误、只缺声明」。

判据本可以在推送时刻看到整批提交信息，没必要逼人改写历史。

## 期望判据（只改读取面，不放宽声明强度）

1. 读取面 = 本次 push 范围 `origin/<branch>..HEAD` 的全部提交信息：
   `git log --format=%B <upstream>..HEAD`。任一提交含合规 `immutable-exempt:` 行即视为该批已声明。
2. 声明与受保护路径的提交**必须在同一 push 批次**内；不得跨分支、跨批次复用（防止一次声明长期生效）。
3. 声明仍须具名、理由 ≥ 现有下限（`MIN_REASON_CHARS`）；签名要求不变；`exit 2` 与「未判定」语义不变。
4. 推送前重写提交信息（amend/reset）仍按新提交判；旧 sha 只在树内容被替换时才需要 superseded 台账，
   「仅补声明、树不变」这一类不再产生台账负担。

## 自指处理（本条判据本身也在受保护面上）

改 `scripts/check-*.mjs`、`scripts/lib/`、`scripts/data/immutable-guard.json` 的提交，本身就在 `[IG]` 射程内。
若按新规则判自己，会出现「规则尚未生效就要先满足规则」的自指。约定：

- **判据版本取父提交**：用被判批次的基线（`<upstream>` / merge-base）里的规则实现来判本批次，
  规则改动只对**后继**批次生效。这样既不追溯改写历史，也不自指。
- 迁移期：本票实现提交在旧规则下被判，因此该提交**在自己的提交信息里**声明 `scripts/check-immutable-guard.mjs`
  与 `scripts/data/immutable-guard.json`，旧规则可识别；合并后新规则接管后继批次。
- `immutable-guard.json` 新增条目同理：本批次新增的路径由**父提交清单**判定（即新条目对自身批次不生效），
  因此「加一条受保护路径」不会反过来要求自己先声明该路径。

## 验收用例

1. 三枚提交，`immutable-exempt` 只写在中间那枚 ⇒ 推送通过（现行为：红）。
2. 声明写在 `origin/<branch>` 之外的旧提交 ⇒ 不通过（禁止跨批次复用）。
3. 改规则实现的批次：按其父提交规则判定；本批次自我声明后通过（自指用例）。
4. `--amend` 补声明后旧 sha 打 `lost-commit/superseded-*`，push 范围只含新 sha ⇒ 通过，且无需再补旧 sha 台账。

## 明确不做

- 不放宽「具名 + 理由 ≥ 下限」；不引入环境变量开关；不把 `[IG]` 降为 warn。
- 不用 commit 之外的位置（分支名/PR 描述/CI 变量）承载声明。
