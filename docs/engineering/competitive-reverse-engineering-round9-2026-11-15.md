## 2. 三道真实红门的诊断与按判据本体修法

**总原则**：三道门都是**真实红门**（门判据本体报红，不是环境噪声），全部**按判据本体**修——即补齐门要求的「如实裁决 / 消费证据 / why」，**不刷基线数值、不改阈值、不用任何跳门变量**。每道门修后单门 RC=0，并做**反向 A/B**（移开补的那一行 → 门转红，恢复 → 门复绿），证明门仍活着、不是被绕过。

### 2.1 `[300]` web `/api/hr-salary-config` 未登记

- **根因**：`scripts/data/api-endpoint-delta-ledger.jsonl` 缺该 web 端点的裁决行，端点增量门按「未登记即报红」判定。
- **按判据本体修法**：向该台账**追加 1 行带 `owner` / `reason` / `evidence` 的裁决**——这是门规要求的登记形态，不是把端点从检查表里删掉。
- **验证实数**：单门 RC=0；门自带 `--self-test` **34 例 0 失败**；反向 A/B（移开该行 → 红 1，恢复 → 绿）闭合。
- **门体代差**：`scripts/lib/scratch-dir.mjs` 为在飞件，仅使用**门自己给出的显式声明出路** `IHUI_GATE_BODY_SOURCE=worktree`（如实落痕，不是跳过）。

### 2.2 `[302p]` `cross-end-drift-gate-baseline.json` unmapped 0→1

- **根因**：新 web 页 `hr/my-payroll` 在 `scripts/data/web-rn-screen-map.jsonl` 的 **HEAD 面缺裁决**，跨端漂移门把「web 有、映射无」计为 unmapped，故 unmapped 从 0 变 1。
- **按判据本体修法**：按门规在该映射台账**补 1 行 `status:gap` 的如实裁决**（RN / 小程序侧现读**零承载**，如实标 gap，不伪造成已对齐）；**不刷基线数值**——基线 JSON 的数字一个没动，修的是映射台账里缺失的裁决。
- **验证实数**：单门 RC=0、unmapped 回到门可接受态；反向 A/B 闭合。

### 2.3 `[304p]` `ChatMessageItem.tsx` 四信号上调

- **根因**：四信号 rpx **39→41** / cssVar **47→48** / className **24→26**，全部由提交 `093e778d7e4` 引入；共享层平台纯度门看到计数上调却缺「消费侧证据」，判为疑似的双端降级信号。
- **按判据本体修法**：按门规在 `scripts/data/shared-layer-platform-purity.jsonl` **第 10 行补 consumption evidence + why**（**消费拓扑未变、非双端降级**）+ **反向断言**——把「为什么这次计数上调不构成纯度退化」写成门可核验的证据，而不是把计数改回去或放宽门。
- **验证实数**：单门 RC=0；反向 A/B 闭合。

### 2.4 为什么这不算「改绿」

1. **没有跳过**：全程未用 `--no-verify`、任何 `SKIP` 变量、任何跳门开关；`IHUI_GATE_BODY_SOURCE=worktree` 是 `[300]` 门**自己文档化的显式声明出路**，且如实落痕，属正常执行路径而非绕过。
2. **没有刷数**：`[302p]` 明确不刷 `cross-end-drift-gate-baseline.json` 的基线数值；`[304p]` 不改回四信号计数、不放宽纯度阈值；`[300]` 不删端点。三处补的都是门规本就要求、但缺失的**裁决 / 证据**。
3. **门仍活着**：三道门各自做了反向 A/B——把补的那行移开，门立刻转红；恢复即复绿。若属「改绿 / 跳门」，移开补行门不会有任何反应。
4. **如实**：`[302p]` 补的是 `status:gap`（承认 RN / 小程序零承载），`[304p]` 补的是「消费拓扑未变」的反向断言，都是把真实状态写成门可核验的证据，不是把红的粉饰成绿的。
