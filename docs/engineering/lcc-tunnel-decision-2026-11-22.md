# 决策记录：放弃 IPv6 直连，通道保持 Cloudflare（2026-11-22）

## 结论

**不做 IPv6 直连。** 现行通道继续走 Cloudflare（反向隧道 `127.0.0.1:2222` + 正向 `ssh lcc` / `prod`），配置不变、约束不变。

本记录的作用是终止这条探索线：避免后续任何人（含自动化 agent）把"开公网 22 换低延迟"重新当成待办捡起来再试一遍。

## 决策依据（全部为本机实测，非推测）

### 1. 当前 sshd 不具备公网暴露的最低防线

`C:\ProgramData\ssh\sshd_config` 全部有效配置仅三行：

```
LogLevel INFO
UseDNS no
PasswordAuthentication no
```

缺失项：`MaxAuthTries`、`MaxStartups`、`AllowUsers`、`LoginGraceTime` 全部未显式设置（走默认值）。

更关键：**未显式关闭 `KbdInteractiveAuthentication`**。OpenSSH 中 `PasswordAuthentication no` 不约束 keyboard-interactive；Windows 上后者走 LSA 密码校验。即"只走公钥"这条硬约束在配置层面并不成立，只是没被触发过。

### 2. 账户锁定阈值会反向杀伤现有通道

`net accounts` 实测：

```
Lockout threshold:                     10
Lockout duration (minutes):            10
Lockout observation window (minutes):  10
```

反向隧道 2222 转发到的是**同一个 sshd、同一个 `Administrator` 账户**。若公网侧出现持续认证失败把该账户锁定，则 2222 这条常驻隧道同时失效——为提速反而打死唯一可用通道，属净负收益。

### 3. 无自动封禁、日志不落地

- 无 fail2ban / sshguard / denyhosts 等任何等价组件。
- sshd 不写 `sshd.log`，日志进 Windows 事件日志。公网暴露后爆破流量将灌入事件日志并要求人工翻查。

### 4. 暴露面背后的资产价值高于便利收益

本机盘上并存：

| 资产 | 路径 |
|---|---|
| GitHub 写权限 token（明文 store） | `D:/DevEnv/secrets/git/github.com.git-credentials` |
| 受保护面签名私钥 | `%LOCALAPPDATA%\IHUI\immutable-guard.key` |
| 追认私钥 | `%LOCALAPPDATA%\IHUI\immutable-guard-ack.key` |
| SSH 私钥 | `.ssh/id_ed25519`、`.ssh/id_remote_control` |

开公网 22 = 把这些资产的宿主对全球可达。一旦失守，损失量级不是"一台机器"，而是"仓库签名权 + 推 main 的权限"。

### 5. IPv6 地址会漂，直连会静默失效

实测本机公网 IPv6：

```
2408:8234:c16:1235:a43f:ec62:a4c5:15b9   Preferred   剩余 2d5h40m45s
```

运营商按租约下发，重拨或前缀变更即变。直连方案必须额外维护 DDNS，多一个会静默失效的零件（表现为"突然连不上"而非报错）。

### 6. CPE 侧改动不可靠且不可白名单化

家用 CPE 的 IPv6 防火墙通常只支持"放行某端口到某内网主机"，无法做源地址约束（对方 IPv6 亦为动态）。固件升级、恢复出厂、运营商 TR-069 远程下发均可能冲掉规则；部分型号改动 IPv6 防火墙会连带影响既有端口映射/UPnP。

### 7. 审计退化 + 新增稳定性风险

- 现行链路的访问记录可经 cloudflared / Zero Trust 侧回溯；直连后仅剩本机事件日志。
- IPv6 端到端中间不做分片，PMTU 发现一旦被黑洞（跨运营商常见），症状为"小命令可跑、传大文件挂死"，且随机复现，比现状的"慢"更难定位。

### 8. 收益与用途不匹配

| 用途 | 判断 |
|---|---|
| 只跑命令、偶尔传文件 | 不值。隧道 0.9 Mbps 传 100MB 约 15 分钟，可接受 |
| 交互式开发 / 频繁小文件 / 远程桌面 | 值，但仅限下述非对称形态 |

直连收益（若成立）：单向 RTT 700–1200ms → 10–30ms，`ssh lcc` 建链 11s → 1s 内。

## 若将来重启此线，唯一允许的形态

**只放行对侧（LICHUNCHUAN）CPE 的 IPv6 入站，本机侧永不开公网 22。**

理由：低延迟需求只存在于"本机 → 对侧"单一方向（`ssh lcc`）。仅暴露资产价值较低的一端即可拿到全部收益，本机（持有 token 与签名私钥）继续藏在 Cloudflare 后面，反向隧道 2222 完全不动。

重启前的前置条件（缺一不可）：

1. 对侧 CPE 规则截图备份，确认可回退；
2. 部署 DDNS 并验证地址变更后能自动恢复；
3. 验证 PMTU（大文件传输不挂死）；
4. 明确记录本机 sshd 的四条补强**不适用于此形态**（本机不暴露，无需改 sshd）。

**任何情况下不允许**：在本机开公网 22 而未先补 `MaxAuthTries` / `MaxStartups` / `AllowUsers` / `KbdInteractiveAuthentication no`，或未加源地址限制、未换非标端口。

## 不可逆性说明

改配置可回退；**暴露不可回退**。端口一旦在公网出现过，扫描记录、指纹与尝试痕迹即永久留在互联网侧，封回去收不回"从未暴露"这个事实。这是本决策最硬的一条理由。

## 保留备选（均不启用）

| 备选 | 状态 | 不启用原因 |
|---|---|---|
| 本机侧 CPE 放行 IPv6 入站 | 未做，已否决 | 暴露签名私钥宿主，风险与收益不匹配 |
| 对侧 CPE 放行 IPv6 入站 | 未做，留档 | 需 DDNS + PMTU 验证，当前无低延迟刚需 |
| P2P 打洞（Tailscale / WireGuard） | 未做，已否决 | 引入第三方控制面、DERP 静默回落、Windows 驱动风险，且违反"不加新隧道/新端口"约束 |

## 现行通道（本次收尾后的既定状态）

| 项 | 值 |
|---|---|
| 反向隧道 | `127.0.0.1:2222` → 本机 sshd，经 Cloudflare |
| 常驻载体 | 计划任务 `IHUI-ReverseTunnel`（SYSTEM，开机+登录+每 2 分钟自检） |
| 正向别名 | 本机 `lcc`、对侧 `prod`（同一条正向腿，cloudflared access + `ihui_ssh`） |
| 本机指纹基准 | `SHA256:ur1rSm+rZW4SL+3SIhJD1tQQs7BHxghNI5hTaMiMoSw` |
| 对侧指纹基准 | `SHA256:0f977g7/MdRbflXH27hBTY48hwfVd+4vZxt7lhGU22c` |
| 体检入口 | `deploy/win/check-lcc-tunnel.ps1`（须 `-NoProfile` 运行，否则 PS7 横幅污染 JSON） |

约束维持不变：只走公钥、只认 2222、不改 sshd/防火墙/CPE、不做公网端口映射、私钥不外传、本机私钥所有者保持 SYSTEM 不回退。
