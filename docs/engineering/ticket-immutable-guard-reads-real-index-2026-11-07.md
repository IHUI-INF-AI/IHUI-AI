# 票：immutable guard 读真实索引，别人的暂存改动会让我方提交判红

## 现象

`git commit --only -- <本次 5 路径>` 时，pre-commit 已通过，但 commit-msg 的 `check-immutable-guard.mjs --staged --message-file` 判红，点名的是 `AGENTS.md（rule-doc / M）` —— 一条本次提交**根本没带**的路径，来自另一条线在共享索引里的暂存改动。结果是：本次提交宣告 `code=undeclared`，被挡在提交前。

## 证据

- 同一条命令：`git diff --cached --name-status -- <5 路径>` 只有 2 条 `M`（本次的 `check-staged-resurrection.mjs` 与 `intentional-file-deletions.jsonl`），另 3 条与 HEAD 逐字节相同；而 guard 的判定面报「改动 2 条 / 命中 1 条」，命中项却是 `AGENTS.md`。
- 说明 `--only` 期间 git 为钩子准备的临时索引（`next-index-<pid>.lock`）没有被 commit-msg 阶段的 `--staged` 读取；它读的是真实 `<gitdir>/index`（此刻挂着别人的暂存面）。
- 用 `scripts/isolated-git.mjs`（每次提交一份私有 `GIT_INDEX_FILE`，`read-tree HEAD` + 只 add 声明集）重跑，同一道 guard 的判定面立刻只剩本次声明集，`AGENTS.md` 不再出现 —— 这是已验证可行的隔离形态（本票只记现象与证据，不写实现方案）。

## 归属

与 `[IG]` 的「读取面」问题同族：判据作用在共享索引而不是本次提交的索引面，于是别人的在飞改动会污染我方结论。应当与 IG 读取面一并处理，而不是各自在调用侧补一层临时索引。
