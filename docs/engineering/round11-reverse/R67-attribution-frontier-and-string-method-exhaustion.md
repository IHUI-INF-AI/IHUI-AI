# R67：归属前沿契约 —— 三条字符串侧判据的实测否证与「前沿」固化

> 目标二进制 `codex.exe` 26.1111.2228.0（382,514,992 B），`.rdata` 74,454,016 B。
> 承接 R66：R65 的「局部逐字节后缀 + 计数唯一」仍是唯一成立判据（44 结构 / 455 字段），
> 三枚结构 `ThreadStartParams`(27)、`TurnStartParams`(28)、`ConfigRequirementsToml`(46) 仍无字段表。
> 本轮把字符串侧能试的三条路一次试到底，全部得负结果，然后把「前沿」固化成可测契约。

## 1. 判据 10：模板后的 16 字节配对记录（否证）

R66 收尾时发现模板区里夹着 16 字节 `(ptr,len)` 记录，且其指向的 blob **以模板结尾**。
当时的读法是「`len` = 该模板前字段文本的精确字节长度」。本轮直接验：

| 结构 | 模板串长度 | 该模板自己的记录 `len` |
|---|---|---|
| `ThreadStartParams` | 41 | **0x29 = 41** |
| `TurnStartParams` | 39 | **0x27 = 39** |

全量核对：2,661 处模板中 **1,323 处**有「end == 模板末尾」的记录，其中 `len` 等于模板
字面量长度的 **1,323 处，不一致 0 处**。也就是说：

- 记录 = 类型名字符串描述符 `(name_ptr, name_len)`，供某处 `&'static str` 用；
- 「end == 模板末尾」的记录共 **1,323 / 2,661** 条，但拿它当字段区边界去切分 **0 命中**——
  因为 body 恒为空（`ptr == 模板起点`）。

**判据 10 作废**。同时更正 R66 报告里「配对记录指向字段区」的猜测。

## 2. 判据 11：合并块切分 —— 字段文本副本没有任何指针指向（否证）

若某结构的字段文本被指针表截断，那张 FIELDS 数组应当就在文本旁边。用 2,197 张 run 库存
在模板前 16 KiB 窗口内查「表项指针落在该段字段文本内」：

| 结构 | 模板前可打印文本 | 命中 run 数 | 表项落文本内的连续段 |
|---|---|---|---|
| `ThreadStartParams` | 158 B（`...tedCapabilityRootsmockExperimentalFieldexperimentalRawEvents`） | 0 | — |
| `TurnStartParams` | 348 B（`...utputSchemacollaborationModemultiAgentModecyberAccessProgram`） | 0 | — |
| `ConfigRequirementsToml` | 451 B（`...oper_instructionsguardian_policy_configguardian_extra_policy`） | 0 | — |

窗口内 **一条 run 都没有指向这段文本**。结论：模板旁那段「字段名连体串」是独立文本副本，
不参与任何 FIELDS 数组；合并块切分在这三枚上无从下手。**判据 11 作废**。

## 3. 判据 12：全局字段名词典 + 唯一最短切分（半成立，精度不够）

既然字段文本是连体串，就用词典把它切开。词典 **不取通用标识符**，而取 R66 库存里
**5,544 个真实 serde 字段名**（12,862 项去重后的干净名），对 2,661 处模板前文本做
「精确覆盖 + 唯一最短切分」：

| 指标 | 实测 |
|---|---|
| 有前缀文本的模板 | **1,706** / 2,661 |
| 能切出（至少一种切分） | **945** |
| 唯一最短切分 | **945**（无歧义，全部唯一） |
| 切出 ≥2 段 | 660 |

**对着 R65 的 44 个真值验精度**：`suffix-ok = 30` / `mismatch = 11` / `no-tail = 3`，
即 **0.732**。失败类型单一且可解释——**相邻真字段被词典里的复合名吞掉**：
`CompactedItemWire` 真值是 `window_id`，词典里存在 `previous_window_id`（别的结构的字段），
最短切分就选了 1 段复合名；`EnvironmentInfo` 同类。

三枚前沿结构在这条路上**一个名字都拿不到**：`ThreadStartParams`/`TurnStartParams`/
`ConfigRequirementsToml` 的字段名不在那 5,544 个名字里（正因为它们的表不存在），
词典切分对「未知词」必然失败。

**判据 12 结论：能做证据，不能做契约。**0.732 的精度写进契约会污染 R65/R66 的基线，
因此不进任何字段表。

## 4. 判据 13：跨间隙拼接（否证，比不拼更差）

假设字段文本被 16 字节记录打断，试「只跨越 ≤24 字节不可打印间隙、窗口 4 KiB」拼接后切分：
**2,661 处只有 1 处能切出**（0.0004），44 个真值 0 复现。拼接会把无关文本接进连体串，
使唯一切分条件彻底不成立。**判据 13 作废**。

## 5. 交付：A14 归属前沿契约

`apps/ai-service/app/core/struct_attribution_frontier.py`（233 行，落地 blob 现读）——把上面四轮的**负知识**
固化成单一真相源，不让后手重跑死路：

| 导出 | 语义 |
|---|---|
| `FRONTIER_STRUCTS` | 三枚未归属结构：`FrontierStruct(name, arity, template_va, template_prefix_tail, blocker)`，`fields_known` 恒 `False` |
| `FALSIFIED_METHODS` | **12 条**已否证判据（R65 六条 / R66 三条 / R67 三条），每条带 `axis`、`why_falsified`（必含实测数字）、`round_id` |
| `MEASUREMENTS` | 9 个实测读数（2,661 模板 / 1,706 文本 / 945 切分 / 30 对 11 错 / 0.732 / 1,323 记录 / 拼接 1 处 / 44 已归属） |
| `unknown_struct_fields()` | `{结构: ()}`——空元组表示「尚未归属」，**不放任何未验证字段名** |
| `can_string_methods_settle(name)` | 前沿结构恒 `False`；非前沿名抛 `KeyError` |
| `validate_frontier(attributed)` | 前沿与已归属契约**必须不相交**；arity 必须为正、`template_va` 必须 `0x` 起 |

`apps/ai-service/tests/test_struct_attribution_frontier.py`（102 行 / 9 例，落地 blob 现读）钉住：
与 R65 契约不相交、前沿不含字段、arity 27/28/46、字符串侧不可解、12 条 id 唯一且稳定、
每条否证理由**必须带数字**、9 个读数与报告一致、前沿陈旧必须报错。

## 6. 验证（全绿）

- 单跑 `pytest tests/test_struct_attribution_frontier.py -q` → **9 passed**
- 五个契约测试联跑（R64 两个 + R65 + R66 + R67）→ **95 passed**
- `ruff check` 两文件 → `All checks passed`（生成器源头修，未用 `--fix` 兜）
- `mypy --strict` 单查模块 → `Success: no issues found in 1 source file`
- 三重变异（arity 27→26 / `pair-record-end`→`pair-record-works` / `0.732`→`0.99`）
  各 **1 failed, 8 passed**，恢复后 sha256 一致 → 转绿
- 水印：两文件 `inject` 后 `verify` 覆盖 2/2

## 7. 诚实边界

1. 前沿三结构的字段名**一个都没拿到**，本轮没有任何猜测性字段进契约。
2. 0.732 的尾部精度只够当证据：它证明「连体串切分」不可作为归属手段，不能反过来当数据。
3. 判据 12 的失败类型（复合名吞并）**不是实现 bug**：词典里确实存在那些复合名，
   而唯一最短切分在信息不足时必然偏短。
4. 三条否证都是**针对这份二进制**的实测结论，换版本需重测；`MEASUREMENTS` 已把它们连同数字钉住。

`ConfigRequirementsToml` 的字段表，只剩定点反汇编：定位引用
`"struct X with N elements"` 的 `fmt` 函数，回溯其 `FIELDS` 实参（`lea` 目标 + 循环上界 27/28/46）。
