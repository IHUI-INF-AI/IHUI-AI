# R66 —— 契约漂移哨兵（A13）+ 归属判据第 8/9 次否证 + 字段表库存落盘

## 1. 本轮定位

R65 把「非 hook struct 的字段名」推进到 44 个结构 / 455 个字段，并把 `ThreadStartParams`(27)、`TurnStartParams`(28) 与 2,532 处模板写明为**未归属**。R66 做两件事：

1. **继续攻归属**：用 PE `.pdata` 的 RUNTIME_FUNCTION 做**机械函数边界**（不反汇编），检验「模板引用与表引用同函数」这条判据；
2. **交付 A13 轴**：把 R65 的 44 条 sha256 指纹做成可运行的**契约漂移哨兵**，让「换版本会不会悄悄改字段」从人工看变成一条判据。

结果：归属判据第 8、9 次实测否证（两个口径都是 0 命中），A13 哨兵落地并全绿。

## 2. 负结果：函数级配对（第 8/9 次否证）

`.pdata` 实测 **13,668,352 B → 1,139,013 个有效 RUNTIME_FUNCTION**（`(BeginAddress, EndAddress, UnwindInfo)`，RVA 三元组），足以给出机械函数边界。

| 口径 | 做法 | 实测 |
|---|---|---|
| 次判据 A（同函数交集） | 模板消息串的引用函数 ∩ 表的引用函数 | `ModelProviderInfo` 表引用函数 `351994`/`954287`，模板引用函数 18 个，**交集为空**；`ConfigToml`、`ThreadStartParams`、`TurnStartParams` 同样为空 |
| 次判据 B（函数内切片） | 只看模板所在函数内部的 `.rdata` LEA 目标，允许「合并表取前 N 项」 | 4 个锚点 `distinct_slices` 全为 **0** |
| 次判据 B′（补 `.data`） | 同上，并把 `.data` 的表与引用一并纳入 | `.data` 只多出 68 个表项、引用从 1,021,037 增到 1,033,156，**切片仍为 0** |

结论：serde 的 `struct X with N elements` 是**独立的 `fmt`/`Display` 实现**，它所在的函数根本不取 FIELDS 表地址；FIELDS 由另一处（序列化/反序列化主体）引用。**距离、函数、覆盖这三类代码侧判据都不成立**，R65 的「字段字面量紧贴模板」是本二进制里唯一已被证实的归属信号。

## 4. 交付（A13：契约漂移哨兵）

| 文件 | 内容 | 判据 | 规模 |
|---|---|---|---|
| `apps/ai-service/app/core/struct_contract_drift.py` | `EXPECTED_STRUCT_FINGERPRINTS`（直接由 R65 契约计算，不另存清单）、`StructDriftReport`（六类：unchanged / reordered / reshaped / renamed / added / removed）、`classify_struct_drift`、`assert_no_struct_drift`、`assert_contract_matches_arity` | 分类按「顺序相同 → 集合相同顺序变 → 长度变 → 内容变」优先级判定，`details` 逐结构给「缺字段 / 多字段」；零漂移守门抛错时点名结构与差异；基线 arity 自检复用 R62 读数 | 177 行（落地 blob 增行）/ 10,255 B |
| `apps/ai-service/tests/test_struct_contract_drift.py` | 六类结论各至少一例 + 守门 + 冻结 + 排序去重 + 指纹复用 | 用「喂观测值」方式覆盖：改名、乱序、少字段、多字段、缺结构、多结构；`assert_no_struct_drift` 必须抛错且消息含结构名 | 152 行（落地 blob 增行） |

关键设计（为什么这是「超越」而不是重复）：

- **单一真相源**：哨兵不复制 455 个字段名，指纹与基线都从 `struct_field_name_contract` 取；R65 契约一变，哨兵基线自动跟随（§0.6）。
- **顺序敏感但分档**：Wire JSON 无序，所以「集合相同、顺序变了」单列 `reordered` 而不混进 `renamed`，避免把等价契约误报成破坏性漂移。
- **可定位**：`details[name] = (missing, unknown)` 让红的那一刻直接指出「哪个结构少了哪个字段」，不需要人再翻报告。

## 6. 诚实边界

1. **哨兵不自带扫描器**：它比较的是「已扫出的结构 → 字段序」，扫表仍靠 R65/R66 的离线脚本；本轮没有把 293 MB 扫描搬进服务运行时。
2. **`ThreadStartParams` / `TurnStartParams` 不在基线内**：若新版本扫到它们，哨兵只会报 `added`，不会假称基线已有。
3. **函数级判据的否证只覆盖本二进制**：`.pdata` 有 113.9 万个函数，本轮的结论是「在这份 26.1111.2228.0 上，模板函数不取表地址」；换编译参数/版本可能不同，不能外推成通用规律。
4. **没有反汇编**：全程段表 + `.pdata` + 字节扫描，Ghidra 未调用；`ThreadStartParams` 的字段表到底落在哪个合并块里，本轮给的是「独立 run 不存在」这一事实，不是归属结论。

## 7. 后续开放轴

1. **合并块切分**：`ConfigToml` 的 118 项合并态已证明「表会被拼接」；若能用「长度档位 + 相邻模板后缀」把 30/33/47 档切回 27/46，`ThreadStartParams` 与 `ConfigRequirementsToml` 就有救。
2. **反汇编兜底**：Ghidra 12.1.4 已装（REA 6.4.0 验证），必要时对 113.9 万函数里那一小批「引用 `struct X with N elements`」的函数做定点反编译，直接看 FIELDS 的实参来源。
3. **跨版本差分**：拿到下一个 codex 版本后，用 R66 哨兵 + R65 扫描器做首次真实漂移比对（这是 A13 的第一次实战）。
4. **非 hook 字段类型层**（R65 §8 遗留）：类型签名仍未取，是 A1 的后半段。
