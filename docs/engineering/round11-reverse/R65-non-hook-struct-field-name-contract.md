# R65 —— 非 hook struct 的 serde `FIELDS` 字段名契约（44 个结构 / 455 个逐字字段名）

## 1. 本轮定位

R62 把轴换到 **arity**，拿到 1,922 条「结构名 + 元素数」的干净读数，但当时**只有元素数、没有字段名**，1136 个 N≥2 未覆盖结构停在「知道几个字段、不知道叫什么」。R63/R64 的字段名/类型是从**内嵌 JSON Schema** 拿的，只覆盖 12 个 hook 家族，不覆盖 `.rdata` 里的 serde `FIELDS` 表。

本轮（R65）攻的正是这条缺口的第一刀：**非 hook struct 的字段名**。结论先行——**44 个结构、455 个逐字字段名、0 歧义**，每一条都带「模板出现次数 / 逐字节后缀字节数 / 后缀覆盖字段数 / 副本表地址」四维证据，并给出 sha256 指纹作为漂移哨点。

## 2. 取证方法的演进（六条否证 → 第七条成立）

这一步必须写全，因为前六条都是**实测失败**，而失败本身是判据可信度的来源。

| # | 判据 | 实测结果 | 否证原因 |
|---|---|---|---|
| 1 | 距离法：字段表起点离 `struct X with N elements` 的引用最近 | 最小距离 947,729 B（ModelProviderInfo） | 真实表引用与模板不在同一函数体邻域，距离量没有判别力 |
| 2 | 内容字符串法：窗口内标识符集 ⊇ 表字段集 | `contained=0` | 字段字面量在 rodata 里**首尾相连**，LEA 目标取到的是 `namebase_url` 这类粘连串，字符串相等永不成立 |
| 3 | 地址包含法：表项 `ptr` ∈ 窗口 LEA 目标集 | `contained=0`（window_vas 39/108/559/189） | 字段字面量**只被表引用**，不被单独 LEA，地址永远不在窗口集里 |
| 4 | 覆盖法：窗口目标的 printable run 覆盖表项 `ptr`（放宽到 prefix/suffix 半张表） | `covered=0` | 窗口指向的是**别的**相邻字面量串，与前缀/后缀都不同源 |
| 5 | 逐字节后缀（只对 4 个锚点） | `hits=0` | 锚点的「模板前文本」被**截断**（run 起点在字段列表中间），整表 24/106 个字段拼起来不可能成为其后缀 |
| 6 | 全局同长表枚举（2,197 张）：仅按「元素数相等」归属 | 24 长度命中 5 张、28 长度命中 1 张、106 长度命中 4 张 | 存在**同长度诱饵表**（`0x15268d160` 24 项 Windows capability、`0x1524672b0` 28 项 `orchestrator_*` 错误码），按条数归属不可信 |
| 7 | **局部逐字节后缀 + 计数唯一**（本轮成立） | **126 处模板命中 / 44 个结构名 / 0 歧义** | 见下 |

**判据 7 的定义（可机械复现）**：对每处 `struct X with N elements` 模板，取其**紧邻之前那段连续可打印文本**（≤2000 B，起点被非可打印字节截断是允许的）；在同为 N 项的候选表里，计算「字段串接」与该文本的**最长公共后缀**；要求该后缀**完整覆盖 ≥3 个字段名且 ≥40 字节**，并且**只有一种不同的字段列表**满足（同一字段列表的编译器副本可多份）。

为什么这条成立：字段字面量在 `.rdata` 里按声明顺序首尾相连，serde 生成 `expecting` 模板时它们就**贴在模板前面**；运行起点被前一个非可打印字节截断，所以只能做「后缀」而不是「全串」。诱饵表在窗口里后缀命中 **0 字节**（内容完全不同源），因此天然出局——这正是判据 6 失败但判据 7 成功的原因。

## 5. 验证（全绿，现读）

- 单跑：`pytest tests/test_struct_field_name_contract.py -q` → **35 passed**
- 联跑 R63/R64 三个契约测试 → **69 passed**（33 + 36，全部机器派生模块互不干扰）
- `ruff check` 两个新文件 → **All checks passed**（生成器直接产出 isort/UP/SIM 合规文本，未用 `--fix` 兜）
- 水印：两文件 `watermark.mjs inject` → `verify` 各 **覆盖 1/1、残迹 0、载荷损坏 0、仅隐写 0**
- 反向变异（三重，红→恢复绿）：模块内 `'capabilities'` → `'capabilitiesX'` **1 failed**；`'oss_provider'` → `'oss_provider_v2'` **1 failed**；`'ConfigToml': 106` → `105` **1 failed**；恢复后 `sha256` 与原文件一致且 **35 passed**

第一处变异最初是「仍绿」——暴露了只钉两个锚点的测试缺口，于是补了**全量 44 指纹注册表**，任一结构任一字段改名都会红。这是本轮测试强度的一次真实修正，记在此处而非事后抹平。

## 6. 与既有模块正交

- R62 只给 arity（元素数），本模块给**字段名 + 顺序**；两者在 44 个结构上逐一相等（`STRUCT_FIELD_ARITY` 就是同源的 N），是**证据互证**而非数据重复。
- R63/R64 的 hook 契约走内嵌 JSON Schema（字段名 + 类型 + 值域）；本模块走 `.rdata` 的 serde `FIELDS` 表，**不 import 也不覆盖** hook 契约，测试 `test_hook_contracts_not_imported_here` 钉住两者集合无交。
- 指纹（sha256）只在本模块内部计算，不复制到别处；A13「契约漂移哨兵」可直接以它为锚点，无需再引入第二份判据（§0.6 单一真相源）。

## 7. 诚实边界（写进账，不当成遗漏）

1. **只覆盖 44/1,136**：R62 的 1,136 是 N≥2 的干净未覆盖结构，本轮只吃到「字段字面量与模板相邻」的那一批。
2. **2,532 处模板的字段串不与模板相邻**：`ThreadStartParams`(27)、`TurnStartParams`(28) 正在此列——它们**不是没有字段表**，而是表的字段字面量与模板不在同一 run；表→结构名归属因此仍缺一条机械判据（前六条已实测否证，见 §2），本轮**不假称已归属**。
3. **3 处无同计数表**：`ThreadStartParams`(27)、`ConfigRequirementsToml`(46) 两处——真实表很可能被相邻表合并（本轮已实测 `ConfigToml` 的 `0x151cc4000` 就是 106+12 合并态），所以「计数不等」不等于「没有表」。
4. **弱覆盖结构**：`ConfigToml` 3/106、`RemotePluginDirectoryItem` 3/18、`ModelProviderInfo` 7/24 属 Tier B——判据靠的是 41–415 B 的逐字节后缀 + 该计数下的唯一性，不是全字段邻接；`STRUCT_FIELD_EVIDENCE.fields_covered` 如实暴露强度，消费方据此分级。
5. **类型层未做**：本轮只有字段名与顺序，**没有**每个字段的 Rust 类型（R64 的类型层只覆盖 hook schema）。这是 A1 的后半段，仍是开放轴。
6. **未做反汇编**：全程只用段表、字节扫描与 `(ptr,len)` 结构解码，没有调用 Ghidra/IDA，因此「函数体内如何消费这些表」不在本轮结论里。

## 8. 后续开放轴（按收益排序）

1. **表→结构名的第二条判据**：以「同函数内 `lea` 的模板引用 + 表引用」做函数级配对（不是距离），目标是把 `ThreadStartParams`/`TurnStartParams` 与 2,532 处未归属模板收回来。
2. **类型层**：serde 的 `FIELDS` 旁边通常还有 `Visitor` 的 `expecting` 类型串（`a string`/`a boolean`/`a sequence`），可望在同一条 `.rdata` 邻接轴上取到非 hook 字段的类型签名，与 R64 的 hook 类型层拼成完整 wire 契约。
3. **合并表切分**：以「计数恰为 N 的前缀/后缀」+ 后缀邻接双约束切分合并表，可回收 `ConfigRequirementsToml`(46) 这类「计数不等」结构。
4. **覆盖账更新**：把 A1 的进度从「0/1,136」改为「44/1,136（字段名层）」，并把 Tier A/B 分层写进 `R64-codex-coverage-and-backlog.md`。
5. **漂移哨兵**：44 条 sha256 指纹已可作 A13 的第一批锚点；换版本时只比指纹，不必重跑 293 MB 扫描。
