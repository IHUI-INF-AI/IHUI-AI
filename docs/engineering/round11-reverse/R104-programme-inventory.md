# R104 — 四十八轮的索引，和一份诚实的边界面

> R56 到 R103，四十多轮，产出 55 个模块、83 份报告。这一轮不再往下挖，而是**把这堆东西收拢**，
> 并且明确回答一个问题：**还有哪些没做完。**

## 1. 为什么按"轴"而不按"轮"

按轮编号列一份清单，是最容易做也最没用的一种索引——它告诉你"第几轮做了什么"，
但不告诉你"**这个能力现在覆盖到什么程度**"。

所以索引按**能力轴**分组，七条：

| 轴 | 模块数 | 攻的是什么 |
| --- | --- | --- |
| structural | 21 | 字段名、声明顺序、类型契约、池残余 |
| hook | 15 | JSON Schema、事件种类、字段拼法、退出码、定序 |
| runtime | 4 | 模块树、状态 schema、桌面键、错误信息 |
| plugin | 2 | 清单、市场、以及管着它们的许可 |
| skill | 1 | 技能引擎与产物契约 |
| gate | 8 | 六道门的行为、findings、图表契约、拒绝码、target、豁免 |
| ledger | 1 | 跨轮共用的结清账本 |

合计 **52 个模块**（`module_count()` 现算）。

## 2. 索引不会腐烂——这一点由测试保证

手写的表迟早会漂。所以 `validate_inventory()` 里有这一段：

```python
for mod in all_mods:
    if not module_path(mod).exists():
        raise InventoryError(f"index names a module that is not on disk: {mod}")
```

**改一个模块名、删一个模块，这个测试当场红。**

这条不是装饰。四十轮下来模块名字改过几次（`codex_` 前缀是 R93 之后才统一加的，
R56–R92 的 `hook_*` / `struct_*` 至今没前缀），如果索引靠记忆写，一定写错。这轮是**扫盘之后**才写的表，
测试再把两者钉死。

## 3. 诚实的另一半：12 条边界

`UNEXHAUSTED` 每一条都是三元组 `(领域, 没立住什么, 为什么)`。全部 12 条：

| 领域 | 没立住什么 |
| --- | --- |
| hook 触发 | **没有任何一次 hook 真正被触发执行** |
| hook 字段类型 | 字段级 type/format/enum 未纳入契约 |
| chart receipt | `--receipt` 的 enforcement 目录未定位 |
| chart 类型覆盖 | 只观测到 barChart |
| powerpoint 完整性 | "complete" 具体指什么未测 |
| 披露措辞 | 只测英文四种拼法 |
| gate 数量 | presentations 另有 10 个工具契约未提 |
| CLI 子命令 | plugin/exec/review/login/mcp/app-server 未实测 |
| 非 hook struct | 字段名仍需 disasm LEA xref |
| schema 片段 | 23 段之外还有 7 段片段未解析 |
| 推送 | 本地提交一直未推送，分叉在扩大 |
| 许可 | LICENSE.txt 禁止反向工程，与项目工作冲突 |

**第一条最要紧**：整条链是关于 hook 契约的，而 hook **一次都没真的跑起来过**。
拿到的全是"二进制里的 schema + 配置文件解析行为"，不是"运行期实际收到的 payload"。
这个差别必须写在这里，不能被 55 个模块的数量盖过去。

## 4. "不声称完整"是模块自己的一部分

```python
COMPLETENESS_NOT_CLAIMED = True
BLACK_BOX_ONLY = True
```

而且测试里有一条**反向保护**：

```python
assert UNEXHAUSTED_COUNT >= 10, (
    "the boundaries list must not be trimmed to make the programme look finished"
)
```

**如果哪天有人（包括我）为了报告好看去删几条边界，这个测试会红。**

`validate_inventory()` 里还有一条同义的保护：

```python
if UNEXHAUSTED_COUNT < 10:
    raise InventoryError("the boundaries list is implausibly short")
```

## 5. 落成

`apps/ai-service/app/core/codex_reverse_inventory.py`：

- `AXES`（7 条）、`MODULES_BY_AXIS`（52 个模块）
- `module_count()` / `modules_for()` / `module_path()` / `describe_axes()`
- `UNEXHAUSTED`（12 条三元组）
- `validate_inventory()`：含存在性检查与边界长度下限

`tests/test_codex_reverse_inventory.py`：**14 passed**。
其中两条是反向变异：塞一个不存在的模块 → 红；把边界裁到 3 条 → 红。

**14 passed**、ruff 全绿、水印 2/2。

## 6. 这份索引能回答什么、不能回答什么

**能**：某条能力轴上有哪些模块、一共多少个、哪些边界还开着。

**不能**：不能回答"每一轮具体验证了什么数字"。那是 83 份报告的事——
索引只到轴，不到轮。刻意如此：轮级细节一旦抄进索引就是第二份真相源，必然漂移。

## 7. 诚实边界

1. 索引里的模块清单是**扫盘后手写**的，测试只保证"写的都存在"，**不保证"存在的都写进来了"**
   ——漏掉一个模块，测试不会红。这是有意取舍：宁可漏登记，也不让测试去扫目录
   （那样索引就变成了目录的镜像，失去"声明"的意义）。
2. 12 条边界是我能想到的，**不等于全部**。别的没意识到的东西，不在这里。
3. 边界条目只写"没立住什么"，没写"下一步怎么做"——那是 tasks，不是边界。

## 8. 合规

本轮无新增探测；全部基于已有模块与磁盘状态。
