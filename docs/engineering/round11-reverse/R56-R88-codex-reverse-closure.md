# R56–R88 — codex.exe 逆向链终局报告

> 对象：`C:/Program Files/WindowsApps/OpenAI.Codex_26.1111.2228.0_x64__2p2nqsd0c76g0/app/resources/codex.exe`（382,514,992 B，Rust PE）
> 手段：只读取证（mmap + 段表解析 + 字符串/记录数组/`lea` 站点对齐），无 Ghidra、无运行期注入、不提取凭据、不复制专有源码。
> 产物：`apps/ai-service/app/core/` 下 27 个契约模块 + 46 个测试文件（2,784 例）+ 报告 20+ 篇。

## 1. 这 33 轮在求什么

一句话：**从 `.rdata` 字节里把这份二进制的结构化契约逐层读出来，读到读不动的边界，并把边界定量化。**

链条是七级递进：

| 阶段 | 轮次 | 求什么 | 关键读数 |
| --- | --- | --- | --- |
| ① 求值域 | R56 | 有哪些字符串 | 1,575,334 条 ASCII 串 |
| ② 求得形状 | R62–R64 | 结构的 arity、hook 契约 | 1,922 条 clean arity；23 段 hook schema |
| ③ 求字段名 | R65–R67 | 非 hook 结构的字段名 | 44 结构 / 455 字段 |
| ④ 求字段表 | R68–R71 | `FIELDS` 在二进制里的物理形态 | 15,234 条 16 B 记录 |
| ⑤ 求声明序 | R72–R76 | 模板序 == 声明序？ | Debug 打印序；池序否证（47%/57%） |
| ⑥ 求全量覆盖 | R77–R86 | 1414 条结构能覆盖多少 | **316 named / 天花板 914** |
| ⑦ 关掉替代路线 | R82 / R87 / R88 | 还有别的入口吗 | 三条全闭 |

## 3. 三条路线，全部闭合

| 路线 | 结局 | 判据 |
| --- | --- | --- |
| 池切分（模板前连排区） | 天花板 914 | R86：500 个结构池内零字节 |
| 模板 lea 配对（同函数内） | **否证** | R82：3,186 个模板的 `lea` 命中 **0** |
| 代码级字符串比较 | **否证** | R88：17,649 个函数，标识符集**中位数 2**，316 个已知字段表**只有 1 个**能在单函数内找到 |

这是"抄尽"最负责的答复结构：不是"我觉得抄完了"，是**把每条可能路径都跑到读数，三条都到顶**。

那 500 个 `empty` 结构的字段名，在这台二进制里不以本链能读到的任何形式存在——不是枚举、不是 derive 的 `FIELDS`、也没有成组的代码字符串。

## 8. 这套东西在工程上有什么用

不是"逆向档案"，是**可执行契约**：

1. **字段名/类型表可当 schema 用**——hook 侧 26 字段、结构侧 316 结构，能直接喂给校验器或文档生成。
2. **`struct_contract_drift` 是换版本的哨兵**——换一份 PE，指纹对不上就逐条点名，取不到 PE 则 exit 2 未判定，不冒绿。
3. **否证结论是可复用的方法资产**——八条被否证的假设，每条都带判据与读数，别人想再试可以直接看到它为什么不行。
4. **天花板是规划输入**——914 这个数字告诉后续任何一轮："在这条路上加判据，最好结果是 914"。

与本仓已有模块正交：这些是只读契约数据，不碰 hook 执行层、不碰鉴权、不碰数据面。

## 9. 诚实边界（五条，不粉饰）

1. **覆盖 63.6%，不是全量**。1436 个结构里 522 个（500 empty + 22 未分类）拿不到字段名。
2. **认证是"逐条"的，不是"整体"的**。完全认证只有 12 项（6 definitions + 3 output 段 + 3 枚举）；316 named 里大多数只是"名字集与池吻合"，`PARTIAL_CLAIMS_ATTESTED=False` 仍在。
3. **仍有未裁决的冲突**：`Failure`/`SetupErrorReport` 共用数组地址 `0x151ad3370`；R75 的 11 个同名多 arity 结构未选副本；与 R65 的 3 个分歧未定夺；池 A 的 4 个前缀碰撞未拍板。这些是"一址多结构"的真实歧义，不是扫描漏项。
4. **`lea` 统计只含 rip-rel `lea`**。用 `mov imm` / `add` 取地址的路径不在 R88 的统计内——这是已知盲区，但 R82 已证模板侧同样无 `lea`，所以主结论不因此动摇。
5. **Ghidra 始终未启用**。整条链 33 轮全部是只读字节取证。Ghidra 能给的是"函数级类型恢复"，那是另一条路，本报告不对它的结果作任何承诺。

## 10. 终局声明

本链到 R88 为止：**三条读字段名的路线全部跑到读数并闭合，覆盖率天花板定量为 914/1436，八条假设被读数否证，12 项契约完全认证，2,784 例测试全绿。**

在"从这份 `.exe` 的字节里继续榨出字段名"这个方向上，**我没有下一步建议**。再往前只有两类动作，都不属于本链：

- 换取证工具（Ghidra 类型恢复 / 动态插桩），那是新的一条链，需要单独评估成本（382 MB PE 的 Java 堆与耗时）。
- 换对象（另一份更新的 PE，或有符号的 pdb），那是"版本比对"而不是"继续深挖"。

若这两类都不做，这条链到此结束。
