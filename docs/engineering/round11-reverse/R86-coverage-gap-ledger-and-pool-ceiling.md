# R86 — 覆盖缺口分类账：池路线的天花板是 914，其中 500 个结构根本没有字段名可挖

## 1. 为什么要做这本账

前几轮一直在"再找一个判据、再多认几个结构"。做到 R85，能说的只是"321 个有字段名、1135 个没有"。这个数字没有回答真正的问题：**剩下的是"还没找到"，还是"根本不在那儿"？**

本轮把 1436 个目录结构名逐个分类。判定用的是"模板前面那段池里能切出多少个标识符"：

| 桶 | 数量 | 含义 |
| --- | --- | --- |
| `named` | **316** | 已有字段表（R75/R80/R81/R82/R83） |
| `under` | 372 | 池里有名字，但少于 arity |
| `over-rejected` | 226 | 池里名字 ≥ arity，但被形状闸拒了 |
| `empty` | **500** | **池里一个标识符都没有** |
| 未分类 | 22 | 在目录里，但模板扫描没匹配到 |

四桶合计 1414 = `STRUCT_ARITY` 的条目数；加 22 个未分类等于目录的 1436。

## 2. 决定性读数：`empty = 500`

这 500 个结构的模板前面**没有字段名字节**（`ConfigToml`(106)、`ToolSuggestDiscoverable`(2)、`OrchestratorToml`(2)、`GhostSnapshotToml`(3)、`RealtimeAudioToml`(3)、`AwsAuthRefreshConfig`(3) 等）。

对它们来说，"池路线"不是"还没扫到"，而是**那里没有东西可扫**。这台机器上再跑十遍池切分，这 500 个也一个都不会变。

要拿它们的字段名，只剩两条别路：
1. 代码里的字符串比较（手写 `serde_json` 路径，例如 `value.get("key")`）；
2. 第二个 schema 来源（本仓目前只有那 23 段 hook schema，覆盖不到这些）。

两条都不在这条链已建的判据里。

## 3. 池路线天花板 = 914

`named(316) + under(372) + over_rejected(226) = 914`。

也就是说：**即使把 372 个 under 与 226 个 over-rejected 全部解开，池路线也只能到 914 / 1436（63.6%）**。剩下的 522 个（500 空池 + 22 未分类）与池无关。

这个天花板值得写进账里，因为它是"再挖一轮池"这件事的边际上限。

## 4. `over-rejected` 看着最可挖，其实不是

226 个"池里名字够数却被拒"的样本说明问题不在判据太严：

| 结构 | arity | 池里切出的名字数 | 前几个名字 |
| --- | --- | --- | --- |
| `FeedbackConfigToml` | 1 | **19** | `Version, In, od, es` |
| `AnalyticsConfigToml` | 1 | 9 | `composer, editor, vim_normal, vim_operator` |
| `FeatureToggleToml` | 1 | 4 | `mermaid, math, tables, lists` |
| `OtelConfigToml` | 11 | 12 | `default, tool_result, log_sse_deltas, log_user_prompt` |

`FeedbackConfigToml` 只有 1 个字段，前面却有 19 个标识符；`AnalyticsConfigToml` 同理。这些名字**属于邻居**——小 arity 结构的模板紧挨着别人的名字池。所以"池里够数"不等于"这些是它的名字"，放宽形状闸只会把这些邻居名字认领进来，而不是解出真字段。

（`FeedbackConfigToml` 里 `Version, In, od, es` 这四个更是切分残渣：`Version` 是真词，`In`/`od`/`es` 是被最长匹配切碎的碎片。）这一点 R75 的形状闸就是在防它。

## 5. `named = 316` 与"321"的差额

跨轮累计的字段表总数是 321（278+23+4+16），但**目录内**只有 316。差的 5 个是 hook schema 名（`*HookSpecificOutputWire` 一类），不在 `STRUCT_ARITY` 里。

另记：`hook-side = 9`（R84 的 6 个定义对象 + R85 的 3 个段），同样在目录外，单独报不并入。

## 6. 交付

`apps/ai-service/app/core/struct_gap_ledger.py`

- `CATALOG_STRUCTS=1436`、`NAMED=316`、`UNDER=372`、`EMPTY=500`、`OVER_REJECTED=226`、`UNCLASSIFIED=22`
- `CLASSIFIED_TOTAL=1414`、`HOOK_SIDE=9`
- `POOL_REACHABLE=598`、`POOL_ROUTE_CEILING=914`、`UNREACHABLE_BY_POOL=500`
- `pool_route_ceiling()` / `empty_share()`（= 500/1436 ≈ 0.3482）/ `validate_gap_ledger()` / `gap_ledger_summary()`

校验器拦：四桶之和 ≠ 1414、分类+未分类 ≠ 1436、可达值与桶不符、天花板算错、桶重叠（和超过目录）、hook-side 被当成目录内、任何桶为负。

测试直接与上游对齐：`CATALOG_STRUCTS == STRUCT_COUNT == 1436`、`len(STRUCT_ARITY) == 1414`、`HOOK_SIDE == HOOK_LOCATED + SEG_LOCATED == 9`——三个数字都不是手写在测试里的孤立常量。

## 7. 验证

| 项 | 结果 |
| --- | --- |
| pytest | **11 passed** |
| ruff | All checks passed |
| mypy（单文件） | no issues |

采集期一处纠错：首版按**模板**累加计数，得 `named=972`——`STRUCT_ARITY` 有 632 个多副本结构，按模板数会把同一名字数多次。改为按名字去重、多副本取"最有利桶"（named > over-rejected > under > empty）后得到 316。

## 8. 诚实边界

1. 分类依据是**池切分结果**，切分本身用 R65 的 20,287 词表 + 最长匹配；词表外的真字段名会被当成残渣，从而把 `under` 低估、`empty` 高估。这是账本的已知偏差。
2. 22 个未分类**没有解释**：目录里有 arity、模板扫描没匹配到。可能是名字长度超出正则上限（60 字符）或模板只出现在 R77 的另一种提取路径里。本轮不追。
3. `empty = 500` 说的是"模板前 2600 B 内没有标识符字节"，不等于"该结构不存在字段名"，只等于"这段邻域里没有"。
4. 天花板 914 是**池路线**的上限，不是整个逆向上限——换判据能突破，但那不是这本账的结论。

## 9. 这本账对"抄尽"的回答

到这里可以给一个不含糊的答复：**池这条路线已经到顶了**。再继续在池/数组上找判据，收益上限是 914；而 914 之外的那 522 个结构，需要的是**另一种数据来源**（代码级字符串比较或第二个 schema），不是更聪明的切分。

这是本轮最重要的结论，也是前几轮"继续再挖"的终止条件。
