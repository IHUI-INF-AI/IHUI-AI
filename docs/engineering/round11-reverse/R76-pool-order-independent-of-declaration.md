# R76 — 池内字节序是与声明序独立的（否证 #6），且池是分片

## 1. 要检验的捷径

R72 用 `lea` 地址序定出了 `TurnStartParams`（25 名）与 `ThreadStartParams`（25 名）的声明序。R73/R75 从池里切出了字段名。于是有一条看似省力的捷径：**池的字节序就是声明序**——若成立，277 个结构的顺序可以一次性从池里读出来，不必反汇编。

本轮就是去量这条捷径。

## 2. 方法

用两个已知声明序的结构做对照（Turn 池 C `0x151b68d78..0x151b68ed4`，348 B；Thread 池 B `0x151b6a548..0x151b6a5e6`，158 B）：

1. 以 R72 的已认证名集合做贪心最长前缀切分，得到**池序**；
2. 取池序与 R72 序的共有名，统计**两两有序对**的一致数 / 不一致数（Kendall 型比较）。

## 3. 读数

| 池 | 池名数 | 共有名 | 一致 | 不一致 | 一致率 |
| --- | --- | --- | --- | --- | --- |
| Turn C | 23 | — | **109** | **122** | **47.2%** |
| Thread B | 8 | — | **16** | **12** | **57.1%** |

两者都在 50/50 随机基线附近。结论不是"池是反序"，而是**池的字节序与声明序独立，不含任何序信息**。捷径不成立：声明序仍只能从 `lea` 站点取（R72 的唯一途径）。

## 4. 一次必须记录的自纠

本轮第一版测量脚本用了 `if ia[x] < ia[y] == (ib[x] < ib[y]):` 这种写法。Python 的链式比较把它解析成 `(ia[x] < ia[y]) and (ia[y] == (ib[x] < ib[y]))`，于是几乎恒为 `False`，首版读数是 **Turn 1 / 230、Thread 1 / 27**——看起来"池序与声明序完全相反"，一个极其戏剧化且错误的结果。

改成分开写两个布尔再比较，真值才是 **109 / 122** 与 **16 / 12**。这两组数字的差别不是精度问题，而是"完全反序"与"随机无关"两种完全不同的结构结论。

因此本模块的所有测度**在导入时从上游模块重算**，不接受任何硬编码常数：模型中若出现"我手写了一个看起来合理的数"，它就再也无法被这条自纠覆盖。

## 5. 第二个发现：池是分片

同一次测量顺带量到了各池的**覆盖缺口**：

| 池 | 池名数 | 结构 arity | 池缺失的已知名 |
| --- | --- | --- | --- |
| Turn C | 23 | 28 | `model`、`summary`、`threadId` |
| Thread B | 8 | 27 | 17 名（`approvalPolicy`、`baseInstructions`、`model`、`modelProvider`、`sandbox`、`serviceTier`…） |

Turn 池还**多出** `cyberAccessProgram`——它在 R72 的 25 名里没有位置（R72 的 `TURN_ORDER_UNPOSITIONED` 之一），但池里确实有这个字面量。

这就把 R75 的 `under 1072`（切出段数 < arity）解释清楚了：**不是切分算法不够好，而是单个池本身装不下一个结构的全部字段**。任何"切完一个池就宣称拿到该结构字段表"的结论，在构造上就是错的。

## 6. 交付

- `apps/ai-service/app/core/struct_pool_order_falsified.py`
  - `TURN_POOL_ORDER` / `THREAD_POOL_ORDER`（直接取 R73 切分，零手敲）
  - `TURN_AGREEMENT` / `THREAD_AGREEMENT` / `ORDER_AGREEMENT`：导入时用正确公式重算
  - `ORDERED_AGREEMENT_THRESHOLD = 0.70`：一致率达到这条线就说明"池确实排了序"，此时否证失效
  - `TURN_POOL_MISSING`（3 名）/ `TURN_POOL_EXTRA`（1 名）/ `THREAD_POOL_MISSING`（17 名）/ `THREAD_POOL_EXTRA`（空）
  - `TURN_POOL_COVERAGE = (23, 28)`、`THREAD_POOL_COVERAGE = (8, 27)`
  - `POOL_ORDER_IS_DECLARATION_ORDER = False`、`POOL_IS_FRAGMENT = True`、`FALSIFICATION_ID`
  - `validate_pool_order_falsification()`：一致率 < 阈值 ∧ 两池都有缺口 ∧ 覆盖未达 arity
  - `falsification_summary()`
- `apps/ai-service/tests/test_struct_pool_order_falsified.py`：10 例

## 8. 诚实边界

1. 一致率只在这两个池上量到。**277 个结构里其余池的序是否也独立，未逐池量**——但既然序不可用，逐池量也不会改变"顺序只能来自 `lea`"这条结论。
2. 两两一致率不是显著性检验。47% 与 57% 都在噪声内，但不做 p 值；本模块给的是**判据线（0.70）**而不是统计结论。
3. `cyberAccessProgram` 在池里但不在 R72 的序里——它的**位置**仍未知，只能确认"名字在镜像里出现过"。
4. Thread 池缺 17 名，说明 Thread 的字段名至少散在 2 个以上池里，但本轮未定位那些池。

## 9. 对后续的影响

- R75 的 277 结构只能声称**名字集合**，不能声称顺序；本模块把这条线写成了可执行的拒止（任何试图用池序当声明序的实现都会被 `validate_pool_order_falsification()` 拦）。
- R75 的 `under 1072` 的正解是**多池合并 + arity 收口**，而不是改切分算法——因为池本身就不完整。
