# R114 —— 尺子本身错了：三次改档与两条错判的撤回

> 上一轮 R113 造了一把尺子，量出 40.4%。这一轮发现**尺子量错了方向**——它漏掉了这条链自己的
> 前半壁。改正比继续量更重要。

## 一、怎么发现的

写 goal 运行时状态时，先查 `.ihui-agent/goal-runtime/`，发现里面已经有别人（同一条链的前序会话）
留下的 `STATE.md`（35,938 B）和 `loop-run-log.md`（**206,508 B**，最后更新 2026-11-18 06:06）。
读它的末尾——**round 20 到 round 27 的收口记录全在里面**：

| round | 交付 |
|---|---|
| 20 | `turn_resume_kind.py` —— ResumeKind 六值封闭集 |
| 21 | `resume_metadata_materialization.py` —— CompactionResumeMetadata 6 元素 |
| 22 | `hook_event_ordering.py` —— 14 项 hook 事件声明顺序 + transcript flush 前置约束 |
| 23 | `fork_dispatch_semantics.py` —— in-process vs out-of-process + fork_turns 三态 |
| 24 | 429 重试 gap 修复 + `error_classify_structured.py`（**唯一接进生产路径的一轮**） |
| 25 | `tool_result_provenance.py` —— tool_result_source 两变体 + 5 字段截断元数据 |
| 26 | `model_reroute_reason.py` —— ModelRerouteEvent 3 元素 + 7 档 reason |
| 27 | `reasoning_channel.py` —— commentary / partial_answer / final_answer 三档 |

**逐个体检**：8 个模块全在 `app/core/`，8 个测试全在 `tests/`。不是空话。

再看规模：报告目录 `docs/engineering/round11-reverse/` 共 **92 份 .md**，`app/core` **311 个模块**，
`tests` **1,311 个测试文件**。

## 二、我错在哪

R113 把账本写成：

- 分母 = 136 个**插件包**实体
- `agent_runtime` 列入**不可达**，理由"无模型端点"
- `binary_semantics` 列入**不可达**，理由"Ghidra 全量零增量"

**两条都错，而且错得代价最大：它们低估了已经做过的活。**

1. **`agent_runtime` 不是不可达。** 用 `strings` 对 `codex.exe` 做静态提取，已经拿到 24 个运行时
   语义面——turn 编排、挂起状态机、resume kind、hook 顺序、fork 派发、工具结果溯源、模型重路由、
   推理通道 phase、错误分类、sandbox 权限请求、execpolicy 门……**每一个都落了模块、报告和测试**。
   "不能真实执行"不等于"语义不可得"。这两件事必须分开算。

2. **`binary_semantics` 更不该判死。** Ghidra 反编译零增量只证明**反编译这条路**不产出增量，
   完全不涉及**别的路能不能到**。而 strings 这条路产出了 24 个语义面——它不是"没做出来"，
   是"用另一种方法做出来了"。

3. **顺带一个更隐蔽的错误**：R113 只有 11 个域，全是插件包。而这条链的 R11–R29（22 份报告）
   攻的是 `codex.exe` 的运行时语义，R56–R91（47 份报告）攻的是结构/枚举层。
   **把它们全漏在账外，等于把 69 份报告的成果记为不存在。**

## 三、改成三档

三种处境本质不同，硬塞进一个百分比必然撒谎：

### 第一档 · 可封闭面（算百分比）

插件包里有**固定数量**的实体，能数清。分母 136，当前覆盖 55 → **40.4%**。
这里的"百分百"是真的百分百：每一个实体都被覆盖。

### 第二档 · 已发现但不可封闭（只报数，不算百分比）

`codex.exe` 382 MB 的语义面。**已经发现 24 个，24 个全部落成**。但"还剩多少个没发现"**无法知道**。

⇒ 对未知分母报百分比是编数。所以这一档**只报"已发现 24 / 已覆盖 24"**，并在 `report()` 里显式写
`semantic_tier_bounded: False`。另计结构/枚举层报告 **47 份**——结构目录不是运行时面，分列。

### 第三档 · 不可达（逐条带证据）

缩到 **3 条**，每条证据长度有下限（<80 字符判错）且禁止 hedge 词：

| key | 理由 | 证据 |
|---|---|---|
| `source_reproduction` | 许可禁止 | LICENSE.txt 1,437 B：reverse engineer / decompile / reproduce / distribute derivative works（R96 逐字读过） |
| `live_execution` | 无模型端点 | R106 三次实测：`/v1/responses` 502、`/v1/chat/completions` 400 与 503 |
| `live_hook_firing` | 触发条件未找到 | R105 五配 + R107 两配全静默；`--dangerously-bypass-hook-trust` 绕 review 不绕 enabled；`enabled` 存储未定位 |

**注意第三条的措辞**：hook 的**语义**已经静态拿到（R16 / R22 / R63 / R105），缺的只是**一次观测到的
真实触发**。把这两件事写成一条，会让人以为 hook 完全没搞明白——所以证据里明写了这个区分。

## 四、`complete()` 的新定义

```
complete = 第一档全绿 ∧ 第二档每个已发现面都被覆盖
```

并且**必须承认**：第二档的"还有多少没发现"不可判定。这不是缺陷，是静态提取 382 MB 二进制的固有性质。
**把这句话写进代码注释里**——否则下一个人会以为我们漏了。

## 六、这次改正的教训

**造尺子比量更重要，而尺子本身也要被量。**

R113 的 40.4% 不是一个"错数"，它是一个**在错误分母上算出的正确比值**——136 里的 55 确实覆盖了，
只是 136 这个分母漏掉了 69 份报告对应的另一半工作。

**下一轮起，每次报告覆盖率必须同时报三档**，任何一档缺一句话都算没报。
