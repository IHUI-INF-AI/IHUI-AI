# R111 — 旋转：框会撒谎，说这个形状不需要那么多地方

> R110 交了一个能抓住溢出的检测器，同时自己把七条边界写在报告第 8 节。这轮补第一条，也是最要紧的一条。

## 1. 为什么旋转必须先补

R110 判越界用的是 **shape 的轴对齐帧** `(x, y, cx, cy)`。**这个帧只在没旋转的时候等于它实际占的地方。**

转 45° 之后，形状的**角**比它的框伸得更远。一个 1,000,000 的正方形，转 45° 后边的长度变成 1,414,214 —— **长了 41%**。

所以 R110 的检测器有一个**系统性低估**：靠近画布边缘、带旋转的形状，它看着"还很宽裕"，其实角已经出去了。**这不是边缘 case，旋转文本框在真实 PPT 里到处都是。**

## 2. 怎么算

旋转不改中心点，只改包围盒的宽高：

```
w' = |cx cos t| + |cy sin t|
h' = |cx sin t| + |cy cos t|
```

中心 `c = (x + cx/2, y + cy/2)` 不动，新帧 = `c - (w'/2, h'/2)` 配 `(w', h')`。

这条公式对任意角度精确，三个自证点：
- **0°** → `(cx, cy)`，原样
- **90°** → `(cy, cx)`，宽高互换
- **45°** → `(cx + cy) / √2`，正方形边长乘 √2

`rot` 在 `a:xfrm` 里以 **1/60000 度**存，所以 `t = radians(rot / 60000)`。

## 3. 那个最能说明问题的案例

造一个正方形，**未旋转时右边还差 100,000 EMU 才碰到画布边缘**：

```
中心 x = 12,192,000 - 600,000
边长   = 1,000,000
原框   = x 11,092,000 宽 1,000,000 → right 12,092,000（差 100,000，安全）
```

转 45°：

```
半对角线 = 1,414,214 / 2 = 707,107
right'   = 11,592,000 + 707,107 = 12,299,107
越界     = 12,299,107 - 12,192,000 - 12,700（容差）= 94,407 EMU
```

**同一个形状、同一个位置，不转是干净的，转 45° 就出去 94,407 EMU。**

测试里这一对**并列**：`straight.pptx` 必须 clean，`turned.pptx` 必须报 `94,407`。一条测试同时钉住"不该报的不报"和"该报的报对量"。

## 4. 和组缩放叠加

组内的旋转子形状要**先缩放再旋转**，顺序不能反：

```
子 cx=1,000,000，组 scale 2 → 绝对框 2,000,000
再转 45° → w' = 2,828,427
中心 12,000,000 → right 13,414,213
```

测试断言 `cx == 2,828,427` 和 `right_emu == 1,209,513`。

**第一版我把这里的期望值算错了**——按 1,000,000 的框算，忘了组已经把它放大到 2,000,000。测试红了一个，逼我回去看 `transform.apply` 和 `rotated_aabb` 谁先谁后。**顺序错了不报错，只报错数。** 这种错静默得最厉害。

## 5. flipH / flipV：不做，这是分析结果不是偷懒

`flipH`/`flipV` 把形状**在同一个框里镜像**，**不改变任何尺寸**。

⇒ 它**不可能**把一个角从画布内挪到画布外。

⇒ 对"越界判定"这个目的，**它不需要处理**。这不是省略，是**证明它不影响结论**。写进 `FLIP_DOES_NOT_CHANGE_AABB = True`，并在 docstring 里说明。

## 6. 落成

`pptx_overflow_detector.py` 增量：

- `rotated_aabb(x, y, cx, cy, rot)` —— 新公开函数，纯算术，可单测
- `_rot_of(xfrm)` —— 读 `rot`，坏值退回 0
- `ROT_UNITS_PER_DEGREE = 60_000` / `ROTATION_AWARE = True` / `FLIP_DOES_NOT_CHANGE_AABB = True`
- `Overflow` 增 `rot_sixtythousandths`（默认 0）+ `is_rotated` + `rotation_degrees`，`describe()` 带 `(rotated 45.0deg)`
- `_walk`：`rotated_aabb(*transform.apply(*frame), rot)`

测试从 19 涨到 **27 passed**，新增 8 条：

| 用例 | 钉住什么 |
|---|---|
| 0° 不变 | 不旋转不误伤 |
| 90° 宽高互换 | 四分之一转 |
| 180° 还原 | 半转 |
| 45° 正方形 √2 | 倍率 |
| ±45° 同 AABB | 对称性 |
| **未转在内 / 转 45° 越界 94,407** | **核心案例** |
| 组缩放 + 旋转叠加 | 变换顺序 |
| 变异：`rotated_aabb` 退化为恒等 → 发现必须消失 | 这层不可或缺 |

## 7. 诚实边界（比 R110 少一条，多的记下来）

1. **组的自身 `rot` 未处理**。OOXML 里组旋转要作用在子坐标系上，我目前的 `_Transform` 只携带平移和缩放，**不带旋转矩阵**。组内子形状自己的 `rot` 是对的（测过），**组本身转了 30° 而子没标 rot 的情况，我算不到**。这是本轮新暴露的、R110 没写的一条。
2. `pic` 的 `srcRect` 裁切仍未处理（按整图框算）。
3. `graphicFrame`（图表/表格）内部绘图区越框未查。
4. **文本溢出层依然看不见**（R110 起就写明，未变）。
5. 只测了我自己造的包，**没在真实 Office 产出的复杂 deck 上验证**。
6. 容差 1 pt 是我定的。
