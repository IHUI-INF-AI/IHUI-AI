# 架构决策记录 · AI 引擎本地/云端切换的范围边界

> 日期:2026-11-15 · 状态:**已定案(采纳)**
> 关联 PoC:`docs/engineering/ai-local-gateway-poc-2026-11-15.md`
> 决策人:机主(授权按深度分析最优建议执行)

## 1. 背景

引擎模式(本地/云端切换)功能已落地三块:
- agent 流(编排 + 工具执行)→ 本地腿直连用户机 ai-service 8803 ✅
- 工具链(`fetchAiServiceJson`)→ 已接引擎模式响应式基址 ✅
- 浏览器 local 连通性 → 生产 CSP 放行本机 ai-service 精确地址 ✅

遗留一个**表面缺口**:普通对话主链 `/ai/chat/stream`(`use-chat`/`getStreamBaseUrl`)未接引擎模式,切"本地"后普通对话仍走服务器网关 8802。

## 2. 决策

**不把普通 chat 流接进引擎本地腿,不做「本地化网关」产品化。**

理由(按权重):

1. **LLM 推理从来不在自家服务器**。PoC 实测:本地栈跑通后真实对话帧是上游 Gemini 返回的 `429 配额耗尽`。切"本地"省的是编排/工具/请求处理算力,**LLM token 推理与费用始终在 LLM 厂商**,切换动不了这块——这是收益的天花板。

2. **成本远超收益**。本地化网关 = 给普通用户打包分发 **网关(api)+ ai-service + PostgreSQL + Redis** 四件套。数月级工程 + 长期维护(升级/迁移/跨版本兼容)。而它只减"普通对话请求处理"这一层低负载。

3. **硬技术门槛**。PoC 实测 Redis 抖动 → token 黑名单 `blacklist.has()` fail-closed → 间歇性 401「Token revoked」。本地档 Redis 稳定性是硬要求,普通用户机难保证。

4. **网关在 chat 链不可绕过**。网关承担压缩、G6 治理、准入配对、预算账本、归档。绕过直调 ai-service 底层会丢这些能力;简单改基址到 8803 会 404(chat 入口在网关,不在 ai-service)。详见 PoC §4。

## 3. 已覆盖场景(足够)

引擎本地切换的"真减负"重头——**agent 编排 + 工具执行**(服务器上最耗算力的部分)——已由前序三块接线覆盖。普通对话走服务器网关的额外负载本身很低,留在服务器是合理终态。

## 4. 为什么这个决策必须记录

"普通 chat 流未接引擎模式"是一个**刻意的设计边界,不是遗漏**。若不固化,后手看到这个缺口会:(a) 当 bug 重做;(b) 重新做一遍本地化网关 PoC。本记录即为此止损。

## 5. 未来重启条件(何时该推翻本决策)

以下任一成立时,可重新评估本地化网关:
- 出现"对话请求处理"成为服务器显著瓶颈的实测证据(非猜测);
- LLM 厂商支持把推理也下放到用户机(如普及的本地推理端点 + 用户机算力足够),届时"本地"才真正动到 LLM 那块;
- 产品形态转变为"自托管/边缘部署"(见 `edge_first_local`,ai-service `config.py:217`),那套形态天然要求本地全套后端。

## 6. 采纳状态

- agent 流接线:✅ 已完成并回归绿
- 工具链接线:✅ 已完成并回归绿
- 浏览器 CSP 连通性:✅ 已完成并回归绿(含守卫测试断言④)
- 本地化网关:⛔ **不做**(本记录定案)
- 普通 chat 流接本地腿:⛔ **不做**(本记录定案)
