# 票：T1 typecheck 假红 —— `tsbuildinfo` 增量缓存与 `rimraf dist` 相撞（每并行分支必复发）

状态：OPEN（专项根治中；本票只做记录与取证，不改门脚本）　　开票：2026-11-08

## 现象（本线实测，两次同形态）

`node scripts/check-typecheck.mjs` 在产物面上判红 / 未判定，但**零 `error TS`**：

```
[typecheck:full] 重建 @ihui/ui-react rc=0 9784ms (陈旧产物 0,复核刷新 0/0,复扫 122)
  - @ihui/ui-react: rc=0, 陈旧产物 0, 已刷新 0, 复扫 122, NOT-OK
[typecheck:full] 重建失败 1 个包 —— 不带着旧产物继续跑类型检查。
❌ 全量 typecheck 失败,推送已阻止(exit 2)
```

复查 `packages/ui-react/dist`：只有 8 个 `.d.ts.map`，**没有 `.d.ts`、没有 `.js`**；
而 `src` 应有 61 个源文件 ⇒ 期望产物 122 个（61 `.js` + 61 `.d.ts`）全部被判 `missing`，
即 `staleArtifacts = 122`。

## 根因（与专项同判）

- `packages/ui-react` 的 `build` = `rimraf dist && tsc`；
- `tsc` 的增量信息落在 `node_modules/.cache/tsbuildinfo/packages-ui-react.tsbuildinfo`，
  `rimraf` 只删 `dist`、不删该缓存；
- 缓存认为“无改动”⇒ 本次 `tsc` 不产出任何文件 ⇒ rc=0 但 dist 残缺；
- `collectPackageState` 的“应有产物缺失”判据（`scripts/lib/stale-dist.mjs:125-139`）于是把 122 个
  产物全判陈旧 ⇒ `ok=false` ⇒ `typecheck-full` 以 exit 2 收尾（不把 NOT-OK 当绿，这点是对的）。

也就是说：**这不是代码红，是增量缓存与构建根之间的键没把“dist 已被清空”算进去**。

## 本线处置（只清缓存，不动门脚本）

1. 删除 `node_modules/.cache/tsbuildinfo/packages-ui-react.tsbuildinfo`；
2. `pnpm --filter @ihui/ui-react build` → rc=0，`dist` 得到 `61 .d.ts / 61 .js / 122 .map`；
3. 再次复现关键一步：若先手工建好再让门的 preflight `rimraf`（缓存已被重建为“新鲜”）⇒ 又退化成
   `复扫 122 / NOT-OK`；
4. 因此正确复跑姿势是：**清缓存后直接跑 `node scripts/check-typecheck.mjs`**，由它自己的 preflight 全量产出：
   `重建 @ihui/ui-react rc=0 (陈旧产物 122,复核刷新 122/122,复扫 0)` ⇒ `T1 rc=0`，`error TS` 命中 `0`，
   `21 个包 typecheck 全部通过` + e2e 通过。

## 边界与复发提示（写给后续每一支并行线）

- 本线**未修改** `scripts/typecheck-full.mjs`、`scripts/lib/stale-dist.mjs`、dist 内容缓存脚本；
  根治（缓存键纳入构建根/清空信号、以及“重建后无产物”的检测口）由专项承担，避免撞文件。
- 只要一支并行分支在自己的 worktree 里首次跑 T1，且该包 `tsbuildinfo` 已在、`dist` 被 `rimraf`，
  就会复现“rc=0 但 0 产物 ⇒ 122 陈旧”的假红。
- 遇到时的最短自救：删该包 `node_modules/.cache/tsbuildinfo/<包名>.tsbuildinfo`，直接重跑门（不要先手工 build 再跑门）。
- 禁止把 `NOT-OK` 读成绿、禁止跳门或 `HUSKY_SKIP_*`；本线按此执行。
