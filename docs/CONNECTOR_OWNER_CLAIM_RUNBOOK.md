# 连接器无主记录认领与两端真机重测手册 (Connector Owner Claim Runbook)

> **最后更新**: 2026-09-29
> **维护者**: IHUI-AI Assistant
> **触发场景**: 部署机上 `connector_store` / `mcp_store` 存在无主记录时 / G-371 属主收窄后的存量清偿 / 三端连接器列表屏改版后回归
> **一条命令**: `node scripts/owner-claim.mjs`(只读巡检 + 生成可复制的认领行)
> **本页管的三件事**: ① 认领存量无主记录 ② 三端真机重测判据 ③ 部署机上装依赖的那条坑

---

## 0. 先确认你在哪台机上(不做完这一步,后面所有数字都没有意义)

**这两件事本质上是"只有换台机器才能做"的活**:`apps/ai-service/data/*.json` 是**每台 checkout 各有一份**的本地文件,
开发机这份的内容推不出部署机那份。所以第 0 步不是礼节,是判据的前提。

现读方式(按当次实测取值,不得把任何一台机的现状当本机事实 —— AGENTS §5b/§15b 各记过一次盘符与机器事实失真):

| 要问的问题 | 怎么量 | 读数说明什么 |
|---|---|---|
| 我是哪台机 | `hostname` | 与部署机名单对上才继续;对不上 ⇒ 下面第 2、3 节在这台机上做不了 |
| 服务在不在 | `netstat -ano \| grep LISTENING` 看 8801/8802/8803/8810/8811 | 一个都没有 ⇒ 这台机是开发机,不是部署机 |
| 数据文件在哪 | `node scripts/owner-claim.mjs` 输出里的 `路径` 那一行 | 打印的是**绝对路径 + mtime**,用它确认你在读哪一份 |

> **这台开发机现在没有 PG、也没有 8801/8802/8803/8810/8811 在监听**(2026-09-29 现读)。
> 因此**第 2 节的认领与第 3 节的真机重测在这台机上做不了,这不是故障,也不是"功能没做完"**。
> 下一个接手的人请先按本节核对机器,再判断是不是环境问题 —— 把环境问题当成开发任务去改代码,
> 是比不做更贵的错误。

## 1. 跑巡检:一条命令,只读

```bash
node scripts/owner-claim.mjs             # 人读
node scripts/owner-claim.mjs --json      # 机器读(三态字段结构化)
node scripts/owner-claim.mjs --self-test # 它自己的不变量证明
```

它同时报**两本账**,且刻意不合并成一个数字:

| 账 | 文件 | 「无主」意味着什么 |
|---|---|---|
| ① 连接器 | `apps/ai-service/data/connector_store.json` | **fail-closed**:该记录对所有人(含原主)读不到 ⇒ 不认领就是「原主永远看不见自己的连接器」 |
| ② MCP 商店 | `apps/ai-service/data/mcp_store.json` | **回退档**(不是读不到):记录全站可见,而 `can_mutate` 对 `owner == ""` 放行任何已登录主体 enable/disable/uninstall ⇒ 不认领就是敞口 |

### 怎么读输出(三态绝不并桶)

| 输出形态 | 含义 | 你该做什么 |
|---|---|---|
| `读到 N 条 … 无主待认领 M` | 已判定 | 进入第 2 节逐条认领 |
| `⚠️ **没有这个文件**` | 未装过 ⇒ 真的零存量,**或**你站错了机器/目录 | 回到第 0 步核对主机名与路径。本工具不因此判红,但也没替你确认「部署机上同样没有」 |
| `❌ **未判定**`(JSON 不可解析 / 顶层不是列表 / 带 BOM / 读不到 / 0 字节) | 这一层**没看见**,不是"没有问题" | 先修可读性再重跑。在它变绿之前,任何「无主 0 条」的结论都不成立。工具 exit 2 |

> **为什么必须先看这一层的颜色,而不是直接看回填器**:实测(2026-09-29)`backfill_connector_owner.py`
> 对「文件不存在」直接打 `记录 0 条` 并 **exit 0** —— 它分不出"真的没有"和"你读错了地方"。
> 三态只在 `owner-claim` 这一层判得出来。

## 2. 逐条认领(只在部署机上做)

对每条无主记录,巡检输出后面直接跟着可复制的那一行。**先 dry-run,再 --apply**,顺序不得跳:

```bash
# 第 1 步:dry-run(把 --apply 去掉即可),只看报告,不写盘
cd apps/ai-service && PYTHONIOENCODING=utf-8 .venv/Scripts/python.exe \
  scripts/backfill_connector_owner.py --claim "yuque:docs=<user_id>"

# 第 2 步:确认报告里"会落 owner"就是你要的那一条,再执行巡检打印的那一行(带 --apply)
cd apps/ai-service && PYTHONIOENCODING=utf-8 .venv/Scripts/python.exe \
  scripts/backfill_connector_owner.py --claim "yuque:docs=<user_id>" --apply
```

`<user_id>` 必须换成真人的 user_id(令牌主体)。**属主只能由人点名** —— 这一族数据里没有
任何可当权威的证据源(记录既无创建者列,也无与会话/记忆的关联键),从别的表"猜"一个属主
等于拿一份不相关的表当授权凭据,比无主更糟。

账 ②(MCP 商店)的行会多带一个 `--store data/mcp_store.json`;不带它就会去写连接器的文件。

### 三条执行前必看的实测告警

1. **同一 key 在文件里出现多条时,巡检刻意不给认领行**(只点名)。实测原因:`plan_backfill` 按 key
   建索引、只看**最后一条**同 key 记录判"要不要落",而 `apply_plan` 会 stamp **所有** key 相同的记录
   —— 于是「一条已属主 + 一条无主」共用同一 key 时,`--apply` 会**连带把已属主那条也改掉**,而
   dry-run 打的是「改写已有属主 0 条」(2026-09-29 临时副本实测:`owner=7` 那条被改成 42)。
   先人工把重复 key 拆开(改名或定性),再认领。
2. **没有 `key` 的无主记录:回填器既看不见也落不了**(`load_store` 里 `isinstance(rec, dict)` 之外的
   过滤就是按 key 收的,非对象条目更是被静默丢弃)。巡检会把它们单独计一堆并报名。出路只有两条:
   人工补一个 key 后再走认领,或按 AGENTS §7 删除安全逐条定性。**不得**为了让它从读数里消失而整片删文件。
3. **key 含 shell 敏感字符**(引号、反引号、`$()`、空格)时巡检同样不出行,改用 JSON 台账:
   `--claims <file.json>`,内容 `{"<key>": "<user_id>"}`。

### 认领完怎么复验

```bash
node scripts/owner-claim.mjs        # 复验判据:账 ① 与账 ② 的「无主待认领」计数都为 0
```

回填器写盘前会把原文件备份成 `<文件名>.pre-backfill-<UTC时间戳>`(留在 data 目录里)—— 认领错了
就从该备份按字节还原,不要手工改 JSON。回填器本身幂等:同一份 claims 第二次跑,落盘项必为 0。

## 3. 三端真机重测(web / 小程序 / RN)

### 判据原文(唯一验收口径)

> **同一部署上两个账号各装一个连接器,互相在列表里看不见、按对方 key 请求回 404 且响应形状与
> "没这条"逐字相同。**

"逐字相同"是判据的核心而不是修饰:如果"不是你的"和"没这条"返回不同,这个端点就变成了
**存在性预言机**(探测别人装了什么)。

### 最小步骤

| 步 | 动作 | 断言 |
|---|---|---|
| 1 | 起 web + api + ai-service(端口见 `docs/port-management.md`),连同一套 PG | 三端能进登录态 |
| 2 | 造两个账号 A / B(注册或既有测试账号;两个都要能拿到自己的令牌主体 user_id) | `A != B` 的 user_id 真实存在 |
| 3 | A 装一个连接器(`yuque:test-a`),B 装一个(`yuque:test-b`) | 各自列表里看得到自己那条 |
| 4 | **A 的列表屏** | 只出现 `test-a`,**不出现** `test-b`(不是"置灰",是不渲染) |
| 5 | **B 的列表屏** | 对称同上 |
| 6 | A 用 B 的 key 直连请求详情/启停/删除 | 404,且响应体字段集与文案模板与"这条根本不存在"**同形** |
| 7 | 三端各跑一遍 4–6 | web / miniapp-taro / mobile-rn 三张列表屏结论一致 |

第 6 步的"同形"按 **HTTP 状态码 + 字段集 + 文案模板** 三项判,不按响应体逐字节判(载荷里带时间戳
与 trace id 时逐字节必不等,那会让用例假红)。

副作用也要断言:越权那一次必须**同时**断言"库里那一行没被动过"(重新用 B 拉一次列表/详情),
只断言 404 会放过"先改了再抛 403"这种写法。

### 与认领的顺序

第 2 节的无主计数没归零之前,**不要**做本节的重测:无主记录对所有人不可见,列表会是空的,
你会把"存量没认领"读成"收窄改坏了"。反过来,认领完立刻重测,才算这条链路闭环。

## 4. 部署机上装依赖的那条坑(会连带废掉全部守门)

**禁止** `pnpm install --filter <包>`。实测(AGENTS §12e):pnpm 会按"只装被选中项目所需"重链接,
顺带剪掉根 `node_modules` 里未被该包引用的链接 —— `lint-staged` 就此消失,`.husky/pre-commit` 第一步
即崩,每次提交都失败并逼出 `--no-verify`,**连带约 110–185 道守门对每次提交全部作废**,而
`git status` 与 typecheck 都看不出依赖树被削。

- 本仓任何"新增/调整 workspace 依赖"一律跑**全量** `pnpm install`(不带 `--filter`)。
- 改完必须验证 `node_modules/lint-staged/bin/lint-staged.js` 与 `node_modules/.bin` 关键入口在位。
- 若已出现"根 `.bin` 缺 shim"(`✖ eslint --fix` / `'eslint' 不是内部或外部命令`):`pnpm install`
  与 `pnpm install --force` 都只回 "Already up to date" 而**不重建 shim**,唯一生效的修复是
  `node scripts/repair-node-bin-links.mjs`;验收看命令本身出不出版本号
  (`node_modules/.bin/eslint --version`、`.../tsc --version`),不看包目录在不在。

## 5. 这台机 vs 那台机:两条常见的误判

| 误判 | 为什么错 | 正确姿势 |
|---|---|---|
| "本机跑 `owner-claim` 报 0 条,所以这活干完了" | 本机那份 `data/*.json` 现读就是 `[]`(2 B),它**不构成**部署机那份的证据 | 认领的读数只在部署机上取;本机跑通只证明**工具能跑** |
| "本机跑测试连不上库 ⇒ 判据没实现" | 本机没有 PG / 服务端口(第 0 步),属环境缺失不是功能缺失 | 按 AGENTS §5 测试隔离铁律:测试一律不得连生产端口;需要库的路径走 mock 或隔离实例 |

## 6. 出口清单(谁改哪一份数据)

| 出口 | 命令 | 是否写盘 |
|---|---|---|
| 巡检 + 生成认领行 | `node scripts/owner-claim.mjs` | **否**(只读;`--self-test` 的夹具写在 `DevEnv/Temp` 临时目录,跑完即删) |
| 连接器/商店属主回填 | `apps/ai-service/scripts/backfill_connector_owner.py [--store …] --claim/--claims [--reassign] [--apply]` | 仅 `--apply`;写前先备份 |
| 无主计数(服务端侧) | `connector_store.ownerless_count()` | 否(只进服务端日志,不返回给调用方) |

`--reassign` 是**改写已有属主**的唯一通道(逐条点名,不点名一律不动)。它存在的理由是"确属登记错了",
不是"懒得问原主" —— 用了就要在交付里点名改了哪几条。
