# SAG2 第五轮：把最后两条挂账做掉 —— OCR 真识别实测 + 规模同口径复测

> 生成：2026-11-09 · 前序 `sag2-round3-20261109.md`（监听/媒体/OCR/建库 229×）、
> `sag2-round4-20261109.md`（PDF 四级链/多跳等价提速 4.4×）。
> 本轮只有两件事：**上一轮如实登记的"未实测"必须变成实测**，以及**发现旧表口径混用并修正**。
> 全部数字为本机现场真跑，OCR 原始 JSON 在 `.ihui-agent/tmp/ocr-run/ocr-probe-fresh.json`
> （`--seeds 3`）与 `.ihui-agent/tmp/ocr-run/ocr-seed1.json`（`--seeds 1`），
> 由 `scripts/sag2_ocr_probe.py` 生成；规模读数在 `.ihui-agent/tmp/quiet-*-r*.json`。

## 0. 一句话结论

扫描件现在**真能读中文字**（干净/轻度退化 CER 0，最差的失焦档 CER 6–9%），
代价是每页 2–4 秒本地 CPU；同时发现 round3 那张规模表把「优化前 5k」和
「优化后 20k/200k」混在一张表里，本轮用同一口径重测并给出区间。

## 1. 补完的挂账①：真实 OCR 引擎在位时的中文识别准确率

### 1.1 环境（可复核）

```
引擎：rapidocr-onnxruntime 1.4.4（onnxruntime 1.28.0，模型随包，CPU）
       + opencv-python-headless 5.0.0.93 / shapely 2.2.0 / pyclipper 1.4.0
python：3.12（本仓 .venv）
status.extractors.ocr = {engine: "rapidocr", installed: true, reason: "", pdf_rasterizer: "pdfium"}
```

装引擎本身有个坑，已写进 `pyproject.toml` 注释：uv 在 `--index-url` + `--extra-index-url`
混合源下解析这棵树 **3 分钟未收敛**，改成 `--no-deps` 精确装只要 **3 秒**。

### 1.2 样本与度量（先说方法，再说数字）

- 样本：程序合成 A4 页（标题 + 6 行正文），正文含可判实体
  （`向量检索` / `王工` / `800` / `940` / `140` / `2026` / `复盘`）；
- 退化：旋转 + 高斯噪声 + 高斯模糊 + 对比度 + 纸张灰度底，另外两档是 JPEG 低质与真 72dpi 版面；
- **CER** = 去空白标点后 Levenshtein ÷ 参考答案长度（111 字）；
- 每档单 seed 跑一遍；关键三档再跑 3 个 seed 给区间。

### 1.3 读数（单 seed，n=1）

档位即 `scripts/sag2_ocr_probe.py` 的 `PROFILES` 键名，读数取自 `--seeds 1`
（`.ihui-agent/tmp/ocr-run/ocr-seed1.json`），无额外档位：

| 档位（PROFILES 键） | 参数 | parser | CER | 关键实体 | ms |
| --- | --- | --- | --- | --- | --- |
| `screenshot` | 干净截图 | rapidocr | 0.0000 | 7/7 | 4665.5（含首次模型加载） |
| `scan-mild` | 0.8°/噪 6/模 0.6 | rapidocr | 0.0000 | 7/7 | 3230.3 |
| `scan-tilt3-noise22` | 3°/噪 22/模 1.6/对比 0.7 | rapidocr | 0.0000 | 7/7 | 2566.6 |
| **`scan-blur2.5`** | **1°/噪 8/模 2.5/对比 0.85** | rapidocr | **0.0901** | **6/7** | 2699.2 |
| `phone-tilt5-noise30` | 5°/噪 30/模 1.2/对比 0.6 | rapidocr | 0.0000 | 7/7 | 2472.6 |
| `fax-jpeg25` | 1°/噪 6/模 0.8/JPEG 25 | rapidocr | 0.0000 | 7/7 | 2403.5 |
| `scan-72dpi` | 0.6°/噪 6/模 0.5/scale 0.48 | rapidocr | 0.0090 | 7/7 | 2393.3 |

### 1.4 三档 × 三 seed（给区间，避免拿偶然当结论）

| 档位 | CER min / median / max | 关键实体最差 |
| --- | --- | --- |
| 3° 倾斜 + 噪声 22 | 0.0000 / 0.0000 / 0.0090 | 7/7 |
| 失焦 2.5px | 0.0631 / 0.0901 / 0.0901 | **6/7** |
| 手机翻拍 5°/噪 30 | 0.0000 / 0.0000 / 0.0000 | 7/7 |

**唯一的显著衰减源是失焦模糊**：CER 6–9%，且会丢掉一个关键实体。
倾斜与噪声几乎不影响：`scan-tilt3-noise22` 与 `phone-tilt5-noise30` 两档三 seed 中位均为 0，
`scan-72dpi` 稳定在 0.0090（单 seed 与三 seed 一致），都是可接受量级。
（读数取自 `--seeds 3`，`.ihui-agent/tmp/ocr-run/ocr-probe-fresh.json`。）

### 1.5 端到端：扫描件进索引后查得到

把「轻扫描 PNG」（`scan-mild`）与「倾斜扫描单页 PDF」（`scan-tilt3-noise22`，脚本写成
`notice-page.pdf`）放进同一目录，走真实链路
（`FolderIngest.register` → `scan` → `Sag2LexicalService.retrieve`）：

| 项目 | 读数 |
| --- | --- |
| 登记 | true（`registered`） |
| 扫描入库（2 个文件，含 OCR） | **4971.4 ms**（`changed=2, failed=0`） |
| 查询「向量检索项目第三季度支出多少」 | top1 = `notice-page.pdf`，score 0.814863 |
| 查询「王工牵头的是哪个项目」 | top1 = `notice-page.pdf`，score 0.592173 |

### 1.6 新发现的真实边界：双栏版面会串栏

同一张双栏页（左栏 2 句、右栏 2 句）经 OCR 后：

```
合同要点 | 乙方负责系统运维与数据备份， | 甲方应按季度提交支出明细， |
并由财务部门复核签章。 | 故障响应不超过四小时。
```

右栏首句被提到左栏之前，右栏两句被拆开 —— **左栏完整、右栏不完整**。
这是引擎按行返回的阅读顺序，不是本仓代码的缺陷。**本轮不改**：按 x 坐标聚类切栏的阈值
风险大于收益（误判会把单栏文档拆乱），登记为已知边界；需要时由调用方按版面坐标系自行重排。

## 2. 补完的挂账②：规模读数同口径复测（并修正 round3 的混口径）

### 2.1 旧表的问题（自查出来的）

`sag2-round3-20261109.md` §5 那张表里：

| 规模 | 建库 |
| --- | --- |
| 5,000 篇 | 40.19 s ← **优化前**（124 篇/s） |
| 20,000 篇 | 2.56 s（修复后，7818 篇/s） |
| 200,000 篇 | 30.57 s ← 优化后 |

5k 那行跑在修 `_remove_chunks` / `_refresh_avgdl` **之前**，和下面两行不是同一份代码。
拿这张表说"建库是线性的"是错的：40.19s → 2.56s 是 16 倍下降，不是线性。

### 2.2 同一份代码、同一台机、连跑两轮

```
python scripts/sag2_scale_probe.py --docs 5000   --rounds 12
python scripts/sag2_scale_probe.py --docs 20000  --rounds 12
python scripts/sag2_scale_probe.py --docs 200000 --rounds 12
```

| 规模 | 建库（两轮） | 快搜 p50 | 多跳 p50 | RSS |
| --- | --- | --- | --- | --- |
| 5,000 | 1.19 / 0.92 s | 7.0 / 5.2 ms | 87.6 / 65.2 ms | 202 MB |
| 20,000 | 4.63 / 3.11 s | 24.4 / 12.9 ms | 246.1 / 126.0 ms | 380 MB |
| 200,000 | 33.35 / 30.61 s | 154.9 / 134.3 ms | 1190.3 / 1017.9 ms | 2415 MB |

**为什么给两轮而不是一个数**：同一台机上两轮同档位可差近 2 倍（20k 多跳 246 vs 126ms），
本机同时有其它会话与守护进程，单点读数不足以当结论。取区间：

- 建库吞吐：**5 600–5 700 篇/秒**，5k/20k/200k 三档一致（线性，无平方级残留）；
- 快搜：5k 5–7ms、20k 13–24ms、200k 134–155ms；
- 多跳：5k 65–88ms、20k 126–246ms、200k **1 018–1 190ms**。

### 2.3 与优化前对比（同机、同脚本、同语料生成器）

| 指标 | 优化前 | 现在 | 倍数 |
| --- | --- | --- | --- |
| 5k 建库 | 40.19 s | 0.92–1.19 s | 34–44× |
| 20k 建库 | 586.71 s | 3.11–4.63 s | 127–189× |
| 200k 快搜 p50 | 365 ms | 134–155 ms | 2.4–2.7× |
| 200k 多跳 p50 | 4845 ms | 1018–1190 ms | 4.1–4.8× |

20k 建库这轮量到 3.1–4.6s 而 round3 记录 2.56s，差值来自机器负载而不是代码回退
（同一 commit、同一脚本；3 seed 的建库波动在探针里是同一路径）。

## 5. 诚实边界（本轮新增/仍然存在）

1. **OCR 样本是合成的**，不是真实纸张扫描/手机拍照。扫描仪坏点分布、装订阴影、页面弯曲、
   印章与手写遮挡都没覆盖 —— 上面 CER 不能外推到"真实合同"，只能说明"印刷体退化图能读"。
2. **双栏版面会串栏**（§1.6），引擎行为，本轮不修，理由已写。
3. **OCR 是本地 CPU 活**：单页 2.4–4.7 秒（含首档 4.7 秒的模型加载），两页 PDF 7.6 秒，
   所以**不适合放进同步请求路径**，只能走文件夹后台扫描（当前实现即如此）。
4. **20 万多跳 1.0–1.2 秒**仍不适合交互式首屏；在线走快搜，多跳放后台。
5. **规模读数有机器负载噪声**（同档两轮差近 2 倍），所以本文一律给区间，不给单点。
6. 真实商业 LLM 打分质量、与线上 embedding 语义等价、51 万规模外推：仍禁说（同前几轮）。
