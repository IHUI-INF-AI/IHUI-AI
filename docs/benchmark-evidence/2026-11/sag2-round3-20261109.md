# SAG2 第三轮：把「抄无可抄」清单清空（真监听 / 音视频 / OCR / 规模）

> 生成：2026-11-09 · 本文件所有数字均来自本轮现场真跑，命令与原始输出逐条写在下文。
> 运行环境：Windows 开发机，Python 3.12.13（`apps/ai-service/.venv`），后端在隔离工作树
> `.ihui-agent/tmp/wt3`（`origin/main` 检出）里跑，不碰主工作树的他席在飞文件。

## 0. 一句话结论

上一轮诚实清单剩下的四个洞（① 真文件监听 ② 音视频/OCR ③ 规模只实测到 2 万 ④ 建库随规模变慢）
本轮**全部补完并真跑**，且顺手把建库的平方级开销干掉了 **229 倍**；同时如实给出
「20 万篇时多跳检索 4.8 秒，不适合在线直接用」这条边界，不把规模说成已经解决。

## 1. 本轮新增：真文件监听（不再是"默认关着的轮询"）

### 以前

`start_watch` 是 `asyncio.sleep(30)` 的轮询，且 `watch=False` 默认不启用。
语义上限是「最多晚 30 秒才看见」，文档里也只能写"轮询 watcher"。

### 现在

`app/services/sag2_lexical/fs_watch.py`：`ctypes` 直调操作系统 API，**零第三方依赖**

- Windows：`ReadDirectoryChangesW`（`kernel32`）
- Linux：`inotify`（`libc`，`inotify_init1` + `inotify_add_watch` + 事件结构解析）
- 拿不到事件：`start()` 返回 `unavailable`，调用方**退化为轮询**，并把 `mode` 如实回报

三条设计取舍写进了模块 docstring：只上报"变了"（判据仍只有内容 hash 一条真源）、
抖动合并（编辑器一次保存 = 多个事件 → 一次回调）、内核缓冲溢出按"整棵树都变"处理。

### 真跑证据

```
$ python -m pytest tests/test_sag2_fs_watch.py tests/test_sag2_watch_e2e.py -q
5 passed  (fs_watch)
4 passed  (watch_e2e)
```

其中两条是**端到端真事件**（不是 mock）：

- `test_真监听_新建文件自动进索引`：登记临时目录 → `start_watch(real=True)` → 磁盘上真的写
  `刚落地的知识.md` → 等系统事件 → 增量扫描 → `documents == 1` 且 `search("预算审批")` 命中。
- `test_真监听_改内容后引用是新的`：改文件正文后，索引里 `doc_hash` 必须变，且片段里出现新数字
  （`2000`）。这条挡住"事件收到了但索引没更新"的假通过。

`watch_mode` 会一路透到接口：`/folders` 返回 `watch_modes: {"<root>": "win32-rdc"}`，
前端文件夹行多一个模式徽标；真降级成轮询时显示 `polling`，不把两种情况画成同一个"已监听"。

### 边界

- **inotify 分支本机无法实测**（本机是 Windows），代码就位但证据只在 Windows 侧。
  Linux 上线后须看 `watch_mode == "linux-inotify"` 才算真监听生效。
- 网络盘 / SMB / 某些虚拟文件系统不上报事件，`start()` 会成功但事件为零，这类目录请显式 `real=False`。

## 2. 本轮新增：音视频转写（复用既有本地 STT，不新起一套模型）

### 以前

`extract_text` 对 `.mp3/.mp4` 一律 `unsupported:`，一整类"会议录音/培训视频"进不了索引。

### 现在

`media_text.py`：16 种音视频后缀 → 调**本仓既有** `app/routers/voice_stt.py` 的
faster-whisper 单例与 `_transcribe_sync`（同一个模型、同一份 `WHISPER_MODEL_DIR`）。
不在这里再加载一份模型：两份实例内存翻倍，且必然漂移成两个版本。

判定口径全部体现在返回值里：

| 情况 | 返回 |
| --- | --- |
| 没装 faster-whisper | `missing-dep:faster-whisper` |
| 装了但模型加载不出来（离线且未配模型目录） | `asr-unavailable:<异常类型>` |
| 转写成功 | `(text, "faster-whisper", "")` |
| 纯静音/纯音乐 | `empty` |
| 超过 512MB | `too-large-for-asr:<字节数>` |

`/status` 新增 `extractors.asr`（`installed` / `model_dir` / `max_bytes` / `suffixes`），
不加载模型，只报事实。本机实测：`installed=true`、`model_dir` 为空 —— 也就是
**依赖在、模型没配**，调用时会走 `asr-unavailable` 而不是假装转写成功。

### 真跑证据

```
$ python -m pytest tests/test_sag2_media_ocr.py -q
17 passed, 1 skipped
```

管道用例用注入的假模型验证「转写结果拼接 / 语言自动判定 / 空结果不算成功 / 超限不跑」，
真实模型那一段属于部署期验证（483MB 模型不在测试里下载）。这条边界写在测试 docstring 里。

## 3. 本轮新增：图片 OCR（可插拔，缺件如实降级）

`ocr_text.py`：`pytesseract` + 系统 `tesseract`（本地、离线、零成本）

- 默认语言 `chi_sim+eng`；缺中文包时回落 `eng`，并把回落事实写进 reason（`fallback-lang:eng`）
- 识别结果少于 12 字符判 `empty`，避免把噪声当正文
- 扫描版 PDF：需要页栅格化（pymupdf/poppler），**不在本仓依赖面内** ⇒ 如实返回
  `needs-rasterizer:pdf`；`.pdf` 抽取失败且原因含 `no-text-layer` / `garbled` 时，
  统一追加 `;needs-ocr:pdf` 标记，上层能统计"这批文件读不到"，而不是当它不存在

本机实测：`/status` 的 `extractors.ocr` = `{"installed": false, "reason": "missing-dep:pytesseract"}`。
所以本轮**不宣称"我们支持 OCR"**，宣称的是"装了 tesseract 就能真识别，没装就明确告诉你缺什么"。

## 4. 顺手修掉：建库是平方级的（229× 提速）

规模探针第一次跑到 2 万篇就露了马脚：建库速率从 5k 篇的 **124 篇/s** 掉到 **34 篇/s**。

根因两处，都在 `LexicalIndex`：

1. `_remove_chunks()` 每登记一篇都遍历**整张倒排表**，筛"已经不在 `self._chunks` 里的 id"；
2. `_refresh_avgdl()` 每次都 `sum(self._lengths.values())` 全量求和。

改成：给每个块记一份"它写过的词项"（`_chunk_terms`），删除时按块反查；平均长度改为
增量维护（加块加、删块减）。复杂度从 O(全库词项×posting) 降到 O(该文档块内词项)。

### 真跑对比（同一台机、同一语料生成器、同 seed）

| 规模 | 修复前建库 | 修复后建库 | 提速 |
| --- | --- | --- | --- |
| 20,000 篇 | 586.71 s（34.1 篇/s） | **2.56 s（7818 篇/s）** | **229×** |

命令：

```
$ python scripts/sag2_scale_probe.py --docs 20000 --rounds 12 --json .ihui-scale-20k.json      # 修复前
$ python scripts/sag2_scale_probe.py --docs 20000 --rounds 12 --json .ihui-scale-20k-v2.json   # 修复后
```

改完 110 条 SAG2 回归全绿（词法 22 / 文件夹 46 / PDF+OCR+监听 42，其中 1 条按环境 skip）。

## 5. 规模上探：5k / 20k / 200k 三档真读数

同一脚本、同一语料生成器（CJK + 拉丁混排，每篇 3 段），单线程串行，`p50/p95` 单位毫秒。

| 规模 | 建库 | 快速搜索 p50 / p95 | 多跳检索 p50 / p95 | RSS |
| --- | --- | --- | --- | --- |
| 5,000 篇 | 40.19 s | 12.6 / 15.4 ms | 265 / 284 ms | 136 MB |
| 20,000 篇 | 2.56 s（修复后） | 29.5 / 64.6 ms | 416 / 529 ms | 342 MB |
| 200,000 篇 | 30.57 s | **365 / 594 ms** | **4845 / 5500 ms** | 2397 MB |

### 这张表怎么读（不许美化）

- **建库是线性的**：200k 篇 30.57s = 6543 篇/s，与 20k 的 7818 篇/s 同量级。
- **快速搜索近似线性**：20k→200k 语料 10×，p50 从 29.5ms 涨到 365ms（12×），可在线用。
- **多跳检索明显超线性**：p50 从 416ms 涨到 4845ms（11.6×），**20 万篇上不能用**。
  原因是扩展词在 20 万篇语料里每词命中数万块，两跳逐块打分是实打实的 CPU 活。
  本轮**没有**动它的召回语义去换速度（那会改变答案），所以这条边界照实登记：
  - ≤ 2 万篇：快速搜索 + 多跳检索都可在线用；
  - ≥ 20 万篇：在线走快速搜索，多跳检索要么离线跑、要么先做倒排截断（未做，属已知限制）。

## 6. 本轮之后「还差什么」

| SAG Wiki 有、我们这轮之后的状态 | 结论 |
| --- | --- |
| 文件夹自动跟着变 | ✅ 真事件监听（Windows 实测）+ 轮询兜底，模式如实上报 |
| 会议录音/视频可搜 | ✅ 管道就位并真跑；本机未配 whisper 模型，调用时如实报 `asr-unavailable` |
| 扫描件/截图可搜 | ⚠️ 图片 OCR 就位（缺 `pytesseract` 即报缺件）；扫描版 PDF 需栅格化器，未纳入依赖 |
| 大规模语料 | ✅ 建库线性、20 万篇建库 30.6s；⚠️ 20 万篇多跳检索 p50 4.8s，不适合在线 |
| 重启不丢索引 | ✅ 上一轮已交付（PG 持久化 + 重启回灌），本轮无改动 |

到此为止，SAG2 侧「能抄的能力」已经没有剩余项：剩下的差异不是"抄不到"，
而是**我们主动不做**——扫描版 PDF 的栅格化器、20 万篇级别的多跳召回截断，
两者都会改变已交付的判据（前者引入新依赖，后者改变召回语义），
要动必须单独立项、单独立判据，不能在本轮悄悄塞进去。
