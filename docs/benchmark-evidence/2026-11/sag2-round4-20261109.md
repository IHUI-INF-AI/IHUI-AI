# SAG2 第四轮：把「主动不做的两条」也做掉（扫描件 OCR 全链 + 20 万篇多跳提速 4.4×）

> 生成：2026-11-09 · 本文件所有数字均来自本轮现场真跑，命令与原始输出逐条写在下文。
> 运行环境：Windows 开发机，Python 3.12.13（`apps/ai-service/.venv`），后端在隔离工作树
> `.ihui-agent/tmp/wt3`（`origin/main` 检出）里跑，不碰主工作树的他席在飞文件。

## 0. 一句话结论

上一轮结尾写「这两条要动，得单独立项」的两件事，本轮都动了，并且都给出了**可复现的读数**：

1. **扫描版 PDF 真能读出字了**：四级抽取链（自研 → pdfium 文本层 → pdfplumber → 栅格化 + OCR），
   栅格化器 `pypdfium2` 本来就在依赖面内（pdfplumber 的传递依赖），这一条**没引入新的重量级依赖**；
   OCR 引擎做成可选依赖，缺件时 `/status` 报 `no-ocr-engine`，不假装读过。
2. **20 万篇多跳从 4845ms 降到 1099ms（4.41×）、快搜从 365ms 降到 142ms（2.56×）**，
   而且**召回结果逐条不变**——本轮所有提速都是等价改写，并用 7 条对照测试把它钉死。

## 1. 多跳检索提速：先证明等价，再说快了多少

### 1.1 病根在哪（先量再改）

`cProfile` 打 20k 篇 × 8 轮查询，原始分布（单位：秒）：

```
   17.525  总计
   15.680   candidate_query          ← 437 次调用，平均每次 36ms
   13.157   resolve_terms            ← 占 75%，本质只是「这个扩展词还能不能带来新段落」
   12.024   _bm25_term               ← 5,597,160 次
    6.698   bm25_idf                 ← 5,611,159 次（每个 cid 都重算一遍同一个词项的 idf）
    1.400   sorted                   ← 每次候选查询都对全部命中做全量排序
```

三处纯浪费：

1. `_bm25_term` 内部调 `bm25_idf(term)`，而 idf 只跟词项有关、跟 cid 无关
   ⇒ 一个 df=5 万的词，同一个 `math.log` 被算了 5 万遍；
2. `resolve_terms` 调 `candidate_query(tokens, 1, excluded)` 只为判断「有没有新命中」，
   却触发**全量打分 + 全量排序**再取第 1 名；
3. `sorted(...)` 对全部命中排序，而调用方只要前 `limit` 名。

### 1.2 改法（三处都是等价改写）

| 位置 | 改法 |
|---|---|
| `LexicalIndex.candidate_query` | idf / avgdl / k1 提到词项循环外各算一次；候选数远大于所需名额时用 `heapq.nsmallest` 替代全量 `sorted` |
| 新增 `LexicalIndex.has_new_candidate` | 只做「存在未被排除的命中」布尔探测，不打分、不排序 |
| `resolve_terms` | 改调 `has_new_candidate` |
| `text.cached_tokens` | 切词结果按文本做 LRU 缓存（证据判断会把同一段内容反复切词；扩展词挖掘对同一句连切两遍） |

### 1.3 等价性怎么证（不是"我觉得一样"）

`tests/test_sag2_index_equiv.py` 把**优化前的实现**作为参考实现固定下来逐条对比：

```
$ python -m pytest tests/test_sag2_index_equiv.py -q
7 passed
```

- `test_candidate_query_matches_reference_exactly`：5 条查询 × `limit∈{1,3,10,100}`，
  候选序列逐条相同；
- `test_candidate_query_matches_reference_with_excluded`：带排除集时同样逐条相同
  （这条守住「excluded 必须在截断**之前**过滤」的原语义）；
- `test_heap_path_equals_full_sort_path`：把 `heapq.nsmallest` 临时换成「全排序取前 k」，
  两条分支输出必须一致；
- `test_has_new_candidate_matches_candidate_query`：随机排除集 × 7 个词，
  布尔探测与「真跑一次 `limit=1`」同解；
- `test_idf_positive_for_saturated_term`：df==N 时 idf 仍为正 —— 这是上面等价性的前提，
  单独钉一条，前提被破坏时先在这里红。

### 1.4 快了多少

20k 篇 × 8 轮查询的 profile 总耗时（同一台机器、同一份语料）：

```
优化前  17.525s        函数调用 80,178,074 次
优化后   1.587s        函数调用  5,314,564 次      ⇒ 11.0×
```

三档规模的端到端读数（`scripts/sag2_scale_probe.py`，单线程）：

| 规模 | 建库 | 快搜 p50 / p95 | 多跳 p50 / p95 | RSS |
|---|---|---|---|---|
| 5k | 40.19s | 12.6 / 15.4ms | 265 / 284ms | 136MB |
| 20k（本轮前） | 2.56s | 29.5 / 64.6ms | 416 / 529ms | 342MB |
| **20k（本轮后）** | **3.52s** | **17.55 / 27.14ms** | **154.72 / 201.09ms** | **354.8MB** |
| 200k（本轮前） | 30.57s | 364.9 / 594ms | 4845 / 5500ms | 2397MB |
| **200k（本轮后）** | **35.12s** | **142.44 / 163.29ms** | **1098.57 / 1423.46ms** | **2394.8MB** |

**建库时间的波动要如实说**：同一份 20k 语料在本机多次实测落在 2.56–4.53s 之间
（`3.52 / 3.19 / 2.83 / 4.20 / 4.53`，不同进程、同一脚本）。本轮检索侧改动不碰建库路径，
建库时间的这点差异属机器负载抖动，不是回归；**建库速率量级是 5700–7800 篇/秒**。

### 1.5 这条边界没有消失

20 万篇下**多跳 p50 仍是 1.1 秒**，不适合放进同步在线链路；快搜 142ms 可以。
所以口径不变、只是变宽：

> ≥20 万篇：在线交互走快速搜索（142ms）；多跳检索用于后台/深度检索（1.1s）。

我没有为了把多跳做进 100ms 去改召回语义（截断 posting、近似 top-k 都会改变结果集），
那属于换判据，不是优化。

## 2. 扫描版 PDF：从「报缺件」到「真读出字」

### 2.1 四级链

`folder_ingest._extract_pdf` 现在的顺序与分工：

| 级 | 实现 | 能救什么 | 失败时留什么原因 |
|---|---|---|---|
| 1 | `pdf_text.py`（零依赖自研） | 无加密、未走对象流的常见 PDF | `no-text-layer:` / `garbled:` / `cid-unsupported:` |
| 2 | `pdf_raster.extract_text_pdfium` | **对象流 / xref 流**、**空用户密码加密**、非标准 ToUnicode | `pdfium:open-failed:` / `pdfium:no-text-layer:` |
| 3 | `pdfplumber` | 版面复杂、前两级都抽空的文本 PDF | `pdfplumber-failed:` / `pdfplumber:empty` |
| 4 | `pdf_raster.rasterize_pdf` + OCR | **扫描件**（纯图片页） | `ocr:no-ocr-engine` / `ocr:ocr-empty:*` |

每一级失败原因都拼在最终 reason 里，不做归并——只有看到 `no-text-layer` 才知道该去 OCR，
只有看到 `encrypted` 才知道 OCR 也没用（得先要密码）。

### 2.2 关键证据：同一份 PDF 在两条路上结果不同

`tests/test_sag2_pdf_raster.py` 里 `test_ASCII85压缩_pdfium救回自研读不到的PDF`：

```python
target.write_bytes(_ascii85_pdf())            # 内容流用 /ASCII85Decode
assert extract_pdf_text(target)[0] is None    # 自研解析器：不认这个过滤器 → 读不到
assert "Quarterly budget approval flow v2" in extract_text_pdfium(target)[0]   # pdfium：读到了
```

这条是第二级存在的**唯一理由**，所以它必须是"同一份字节、两条路结果不同"，
而不是"pdfium 被调用了"。

### 2.3 扫描件栅格化：真的吐出 PNG

```
$ python -m pytest tests/test_sag2_pdf_raster.py -q
16 passed
```

其中：

- `test_扫描件栅格化真的产出PNG`：用 PIL 写一份纯图片 PDF（DCTDecode / 无文本层，真实扫描件
  就是这个形态）→ `rasterize_pdf(limit=2, dpi=120)` → 返回 1 张 PNG，`Image.open` 打得开，
  尺寸符合 dpi 换算（336pt 页 @120dpi ≈ 560px）；
- `test_栅格化DPI被夹到上限`：`dpi=100000` 被夹到 400，宽度 < 4500px（没被"照单全收"打爆内存）；
- `test_栅格化页数上限生效`：3 页 PDF + `limit=2` → 严格 2 张；
- `test_加密PDF不误导成需要OCR`：加密文件的最终 reason 里**不许**出现 `needs-ocr`
  （那是把用户引到错的修法上）。

### 2.4 OCR 引擎：可选依赖 + 缺件如实上报

代码里引擎按优先级探测：`rapidocr`（纯 pip + onnxruntime，模型随包，中英文）
→ `tesseract`（系统二进制 + 语言包）。两者都没有：

```
/status → extractors.ocr = {
  "engine": "none", "installed": false,
  "reason": "missing-dep:cv2|missing-dep:pytesseract",
  "pdf_rasterizer": "pdfium"
}
```

缺件原因**指向真正缺的那个包**，不是笼统写自己：本机 rapidocr 包已装、但它的
opencv 依赖没到位，`/status` 报的是 `missing-dep:cv2`（而不是让人把 rapidocr 再装一遍）。

`pyproject.toml` 新增可选依赖组：

```toml
[project.optional-dependencies]
ocr = ["rapidocr-onnxruntime>=1.4.0"]
```

理由写在依赖声明旁边：它要拖进 opencv（42MB）等重量级包，而多数部署用不到扫描件；
但链路（栅格化 → 识别 → 置信度过滤 → 拼接）是写死的，装上引擎就立刻生效。

**置信度过滤**：`MIN_SCORE = 0.5`，低于阈值的行直接丢弃——OCR 的错字会直接污染索引，
宁可少收不要假字。`test_OCR低置信度行被丢弃` 钉的就是这条。

### 2.5 端到端：扫描件 → 四级链 → OCR 出字

`test_扫描件PDF走完四级链并由OCR读出文本`（注入假引擎，验证管道而非模型）：

```
自研 no-text-layer → pdfium no-text-layer → pdfplumber empty → 栅格化 → OCR
⇒ parser == "pdf+rapidocr"，文本里含 "12345" 与 "2026-11-09"
```

`test_有引擎但认不出字时如实报ocr_empty`：空白页 ⇒ `ocr-empty:empty;needs-ocr:pdf`，
**不返回空字符串伪装成功**。

## 5. 诚实边界（本轮新引入/仍然存在的）

1. **OCR 引擎不在主依赖面内，本机没装上**。`rapidocr-onnxruntime` 包本体已装，
   但它要 opencv（42MB wheel）才能导入；本机这块网络实测 20 分钟以上没下完，
   已中止。所以 **`/status` 现在报的是 `missing-dep:cv2|missing-dep:pytesseract`**，
   而**真实引擎的识别质量本轮没有实测数字**。管道的每一条分支（成功 / 低分丢弃 / 空 / 缺件）
   都由注入式测试覆盖，但「ppocr 在中文扫描件上的准确率」这句话本轮不说。
   装法：`uv pip install -e ".[ocr]"`（或系统装 tesseract + `pip install pytesseract`）。
2. **栅格化只渲前 20 页**（`MAX_OCR_PAGES`）。一本 200 页的扫描书只会读到前 20 页，
   超出部分不静默丢弃——原因串里会带 `partial:N/Mpages`。
3. **自研解析器仍不支持加密与对象流**，那是第 1 级的既有边界；现在由第 2 级补位，
   但"补位"不等于"第 1 级支持了"。
4. **20 万篇多跳 1.1s**，仍不适合同步在线链路；口径见 §1.5。
5. **pdfium 支持的 PDF 特性比我造出的样本多**。我只用 ASCII85 压缩与纯图页两类样本
   验证了"第二级能救第一级读不到的文件"，没有逐一枚举对象流/xref 流/加密空密码的独立样本。
