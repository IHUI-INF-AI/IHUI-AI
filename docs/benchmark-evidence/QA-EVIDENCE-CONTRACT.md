# 取证与 QA 口径规范（RP-23 / L16）

适用面：`docs/benchmark-evidence/**` 下的对标报告、QA 报告、账本 JSON，以及任何引用这些结论的计划/收口行。本文件是结论标注的唯一口径；机器判据在 `scripts/check-qa-evidence.mjs`。

## 1. 三档证据标注（每条结论必须且只能属于一档）

| 档 | 键名 | 成立条件 | 禁止措辞 |
|---|---|---|---|
| 产品级闭环 | `product_loop` | 有真实模型输出原文（SSE `delta.content` / markdown 文本，且非回声验证），并有可复核账本路径 | "已闭环"用于仅有 HTTP 200 / 端口 / UI 静态面的对象 |
| 框架运行态 | `framework_runtime` | 有进程、端口、日志、HTTP 状态码、UI 或源码静态证据，但**不是**模型推理输出 | "模型已回答""推理结果" |
| 未知 | `unknown` | 凭据不足、协议未打通、仅有静态字符串，或证据互相矛盾 | "已验证""闭环""绝不会" |

三档之外不许自造第四档（如"半闭环""基本可用"）。档位写在 `evidence_tier` 或结论所属数组键上，二者冲突以档位字段为准并判违规。

## 2. phase 快照与模型输出分离

- `phase_snapshot` 只记录状态机迁移（如 `initializing → streaming → done`）与触发时间，字段里不得混入 `delta.content` / `markdown` 原文。
- `model_output` 只记录真实模型输出片段与来源帧类型，字段里不得混入 phase 状态。
- 两者不得是同一段文本/同一个对象；无法分离时把结论降为 `unknown`，不许合并成一条"既是状态又是输出"的证据。

## 3. 202 / 401 / refusal 不得写成模型闭环

`202 Accepted`、`401 Unauthorized`、`403/404`、`refusal`、`Authentication required` 只证明请求被接受或被挡在传输/鉴权层。结论文本中出现这些词时，必须同时出现明确的边界说明（"传输层通、模型层被挡""未发 prompt""未证明推理输出"）。

**禁止**：把这些状态码或拒绝响应写作"模型返回""模型闭环""推理完成"。校验脚本扫描 `product_loop` 档条目的 `evidence` / `boundary` 字段，命中肯定措辞即判红。

## 4. 每条结论挂可复核账本路径

`product_loop` 每条结论必须有非空 `ledgers` 数组，元素形如 `analysis/<name>.json` 或 `docs/benchmark-evidence/**`，并写明 `ledger_verified`（复核过哪一条、复核到什么值）。没有账本路径的结论只能降到 `framework_runtime` 或 `unknown`。

脚本对账本**声明完整性**判红，对账本**文件当前是否存在**只报 warning：历史账本可能随清理移走，缺失不等于结论造假，但必须显式可见，不能静默。

## 5. 机器判据与边界

```bash
node scripts/check-qa-evidence.mjs --report docs/benchmark-evidence/2026-11/report-qa-2026-11-26.json
node scripts/check-qa-evidence.mjs --self-test   # 逐条变异咬合
```

判据集合：三档定义齐全（B1）、三档结论面齐全（B2）、产品级条目账本声明齐全（B3）、档位措辞不交叉（B4）、状态码/refusal 不写成模型输出（B5）、phase 与 model_output 不合并（B6）。

**边界**：本门只做证据 JSON 的结构与措辞审计，不重放网络请求、不核验账本 JSON 内容的真伪、不判断业务功能是否真的可用；结论是否成立仍需人工复核账本原文。
