## 二、缺陷清单（按严重度排序）

### 🔴 F1 — 类型检查门禁红灯（阻断级，已修复）

- **位置**：`apps/web/src/components/chat/message-input.tsx:350` 与 `apps/web/src/hooks/use-message-send.ts:39`
- **现象**：`pnpm typecheck` / CI 退出码 2，仓库硬门禁（AGENTS.md 要求 typecheck 0 错误方可合并）实际失效。
- **根因**：
  1. `use-message-send.ts:39` 接口声明误用 `React.DropEvent`（React 19 不存在该类型，应为 `React.DragEvent`，而 `handleDrop` 实现体 line 137 用的就是 `DragEvent`）。
  2. `message-input.tsx:350` 调用 `setPendingMessage(null)`，但 `useMessageSend` 内部虽有 `setPendingMessage` 状态 setter（line 104），**未将其暴露到返回对象/接口**，组件仅解构了 `pendingMessage` / `sendPendingMessage`。
- **影响**：聊天输入框「流式期间取消预备消息」功能在编译期即报错；任何基于 typecheck 的 CI/合并被阻断。
- **修复**（已应用并复验）：
  - `use-message-send.ts`：`DropEvent` → `DragEvent`；在 `UseMessageSendResult` 接口与 return 对象中补暴露 `setPendingMessage`。
  - `message-input.tsx`：从 `useMessageSend` 解构补 `setPendingMessage`。
  - 复验：`pnpm --filter @ihui/web typecheck` 退出码 **0**，全量 `typecheck-full.mjs` 复验通过。
- **遗留建议**：本次 2 处错误位于已提交文件（非本次工作区改动），说明此前某次提交绕过了门禁。建议排查为何能合入（pre-commit/CI 是否实际执行 typecheck）。

### 🔴 F2 — deploy-lock 悬挂锁无限死循环（潜伏 P0，已加固）

- **位置**：`scripts/deploy-lock.mjs` — `removeLock()`(line 61-67) 与 `acquire()`(line 109-115)
- **现象**：若 `acquire` 遇到悬挂锁（持有进程已死 + 超 stale）并调用 `removeLock()`，而 `rmSync` 因**任何原因失败**（Windows 文件被其他进程锁定、权限、路径为 junction 等），错误被 `removeLock` 的 `try/catch` **静默吞掉**，目录仍存在 → `continue` 进入下一轮 `for(;;)` → 再次 `mkdir` 失败 → 再次静默失败 → **永久自旋**，构建/启动永远卡住。
- **根因**：`removeLock` 吞掉所有异常，且 `acquire` 在删除后未校验是否真删成功即 `continue`。这正是 2026-08-14 记忆中记载的事故模式。
- **触发面（重要修正）**：经 `grep` 确认，`deploy-lock.mjs` **仅被 `scripts/build-next-prod.ps1` 引用，并未接入 `start-dev.ps1` / `pnpm dev`**。记忆中「`pnpm dev` 启动遇悬挂锁死循环」的触发路径与当前代码不符——该脚本不在 dev 路径上。但缺陷本身在 `build-next-prod.ps1` 的 prod 构建路径上仍是真实定时炸弹。
- **修复**（已应用）：在 `acquire` 的抢占分支、`removeLock(dir)` 之后增加 `existsSync(dir)` 校验——若目录仍在，直接 `throw` 退出并提示用户手动删除，杜绝 `continue` 死循环。

### ⚪ F6 — `@ihui/ui-react`「陈旧 dist」误报（低危 / 门禁校准问题，已修复 ✅）

- **位置**：`check-stale-dist` 标记 `dist/index.js` 不存在
- **真相**：`packages/ui-react/package.json` 的 `exports` 为 `"import": "./src/index.ts"`，即**从源码消费**，不依赖 `dist`。故该告警为**误报**，非真实产品缺陷。
- **影响**：`pnpm check:all` 因此项退出码 1 而整体失败（链式 `&&` 在 stale-dist 处中断，后续 guard 未执行）。
- **建议**：修正 `check-stale-dist.mjs`，对 `exports` 指向 `src` 的包跳过 dist 校验，避免 CI 误红。

> **修复结果（2026-08-15 ✅）**：`scripts/check-stale-dist.mjs` 已修正——新增 `isConsumedFromSource(pkg)` 判定（检测 `main`/`module`/`exports` 指向 `./src/**` 或 `.ts/.tsx`），对"从源码消费"的包跳过 dist 校验。现 `check-stale-dist` 对 12 个 packages 全部判定为 skip/同步，退出码 0，CI 不再误红。

### 🟢 F7 — 测试套件失败修复（用户侧 F5，已修复 ✅）

- **范围说明**：对话中用户确认的 F5 =「跑全量 test 套件并修复失败」，与报告内 F5（dead migration）为不同事项，此处单列。
- **结论**：`@ihui/api` 与 `@ihui/mobile-rn` 全量测试现已 **0 失败**——api **358 文件 / 5943 测试**全绿，mobile-rn **18 文件 / 198 测试**全绿（复跑确认，本次未改动）。
- **根因与修复**：
  1. **auth 路由测试 500（系统性回归）**：2026-08-06 引入 `setAuthCookies`（httpOnly cookie）+ 2026-08-14 `csrfPlugin` 重构（不再自行 register `@fastify/cookie`，依赖父作用域），导致 8 个注册 auth 路由的测试 app 未注册 cookie 插件 → `reply.setCookie is not a function` → 500。修复：在 `beforeAll` 中 `await app.register(cookie)`（`auth.test.ts`、`auth-oauth-server`、`auth-permission`、`auth-sso`、`success-paths`、`auth-apple-callback`、`auth-extended` 共 8 处）。
  2. **analytics/track 误判 401**：`POST /api/analytics/track` 是公开埋点端点（匿名可上报，见 `analytics.ts` 注释 + `csrf.ts` PUBLIC_PREFIXES 白名单），但 `auth-negative.test.ts` / `misc3-routes.test.ts` 将其列入「无 Bearer → 401」清单（且测试 app 未注册该路由，实际返回 404）。修复：从 401 清单移除（符合文件既有公开端点排除约定）。
  3. **comments.test.ts `SAMPLE_UUID is not defined`**：编码损坏导致 `const SAMPLE_UUID` 被并入 `//` 注释行而失效。修复：拆分为独立声明行。
  4. **51 个测试文件中文编码损坏（编译不过）**：工作区 51 个测试文件的中文串被某次批量操作损坏（字符串闭合引号被吃掉，esbuild 报 `Unterminated string literal`），而仓库 HEAD 为干净 UTF-8。修复：从 `git` HEAD 恢复这 51 个文件（工作区相对 HEAD 的改动纯属损坏，无正经代码丢失）；`success-paths.test.ts` 恢复后补回 cookie 注册。
  5. **csrf.test.ts 过期 mock**：原 `vi.mock('@fastify/cookie')` 注释称「真实包 ESM 加载失败」已被证伪，且该 mock 因 csrfPlugin 重构后不再 import cookie 而无引用方 → 测试 app 缺 cookie 插件 → 500。修复：删除过期 mock，改用真实 `@fastify/cookie` 注册（与其余 8 处一致）。
- **环境前置（非代码缺陷，已规避）**：本机默认测试临时目录 `D:\caches\Temp` 偶发 `EPERM`（rename 被拒），导致个别文件转译失败；指定可写 `TEMP`（如 `C:\Users\Administrator\AppData\Local\Temp`）后全绿。CI/正常环境无此问题。
