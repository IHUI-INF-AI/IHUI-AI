# 服务器 Agent 任务指令 —— 一键部署管道 + 云端并行沙箱 worktree

> 用途：把本文件中两个"粘贴块"分别发给生产服务器上的 agent（aizhs.top 所在机器）。
> 发送顺序：**先任务一（部署管道），跑通后再发任务二（沙箱）**——两者共享同一台机器资源，不要并发。
> 建议一次只发一个粘贴块，等验收报告回来再发下一个。

---

## 发送前你需要准备的东西

1. 确认服务器 agent 有 **sudo/root 权限**（nginx、docker、systemd 都要动）。
2. GitHub 仓库（`IHUI-INF-AI/IHUI-AI`）的 **admin 权限**（用来加 Actions secrets）。如果服务器 agent 没有 gh 凭据，它会回传需要你手动添加的 secrets 键名——你在 GitHub → Settings → Secrets and variables → Actions 里加即可。
3. 部署专用 SSH keypair：可以让服务器 agent 自己生成，或你提供现有私钥。
4. 测试账号：e2e 已有 `admin/admin123`、`test@aizhs.top/Test@123456`，供线上登录验证用。
5. （可选，顺带办）桌面端签名 secrets `DESKTOP_TAURI_PRIVATE_KEY` + `DESKTOP_TAURI_KEY_PASSWORD` 也一直缺失，如果你手上有签名私钥，可在加部署 secrets 时一并加上，release-desktop 四平台流水线即可复活——此事与服务器 agent 无关，勿让它碰。

## 任务一粘贴块：一键部署管道打通

```text
你在 aizhs.top 生产服务器上。IHUI-AI 是 pnpm monorepo（GitHub: IHUI-INF-AI/IHUI-AI，主分支 main），
生产站点 = https://aizhs.top，采用 nginx 蓝绿部署。仓库内 deploy/ 目录已有蓝绿部署脚本与 nginx 配置，
GitHub Actions 已挂 push 触发：deploy/nginx/** 变更即触发部署 workflow。该 workflow 历史全部失败在 SSH 步骤，
根因是 GitHub 仓库级 secrets 从未配置：DEPLOY_HOST / DEPLOY_USER / DEPLOY_SSH_PRIVATE_KEY。
另外仓库版 nginx 配置新增了 /v1 与 /ws 两个 location（分别代理 LLM 网关与 WebSocket），待线上同步。
本机开发端口参考（web 8801 / api 8802 / ai-service 8803），生产端口以你盘点为准。

目标：让「git push → 自动部署 → 健康检查 → 切流 → 失败自动回滚」全链路真实跑通，并完成线上验证。

第一步 盘点（只读，不改任何东西）：
1. clone/更新仓库到服务器（如 /opt/ihui），通读 deploy/ 全部脚本与 nginx conf、.github/workflows/ 里的部署
   workflow，输出一页现状：蓝绿两组端口、服务管理方式（systemd/docker/pm2）、当前蓝/绿哪组在跑、
   health 端点路径、回滚脚本是否存在及可用。
2. 核对服务器实际拓扑与仓库脚本的假设是否一致（端口/路径/服务名/证书路径），不一致处列成清单先回报再动。

第二步 打通 secrets：
- 生成部署专用 SSH keypair（deploy@ 专用，禁用 root 直登则按仓库脚本要求配置）；
- 把 DEPLOY_HOST / DEPLOY_USER / DEPLOY_SSH_PRIVATE_KEY 写入 GitHub 仓库 Actions secrets
  （你有 gh admin 就自己加；没有就把三个键名与需要我手动加的说明回传给我）。

第三步 部署链路自检与修复：
- 验证蓝绿脚本幂等：连续执行两次部署，第二次必须无副作用（服务不重启、nginx 不重复写配置）；
- 验证 health check 门禁：健康检查不过时必须不切流，且自动回滚路径可用；
- 手动触发一次完整部署（Actions 或脚本），全程日志留档。

第四步 线上同步与验证：
- 把仓库版 nginx 配置（含 /v1 /ws）同步到线上 nginx 并 reload（reload 前先 nginx -t，旧 conf 备份）；
- 后端发版使 tauri.localhost 进入 CORS 白名单（这是遗留待办，改完随部署一起上线）；
- 生产验证四项：① aizhs.top web 页面可用；② /api 登录可用（测试账号 admin/admin123）；③ /v1 LLM 网关可达；
  ④ wss WebSocket 握手成功；
- 生产 web 部署到最新 main，并复测工作区链路：登录 → 添加本地工作区 → AI 能读取工作区文件内容。

验收（全部满足才算完成）：
1. push 一个 docs-only commit 能自动触发部署并成功上线；
2. 人为注入一次部署失败，系统能自动回滚且线上无感知；
3. 第四步四项线上验证全部通过；
4. 产出《部署管道验收报告》：拓扑说明、端口表、secrets 清单（只列键名不贴值）、回滚演练记录、遗留风险。

红线：禁止 force push；禁止动 main 上并行会话的未完成改动；生产操作前先备份 nginx conf 与数据库；
一切变更先在非在跑的那组（绿/蓝）验证再切流；不得开放无鉴权的管理端口；可用性优先，出问题先回滚再排查。
```

## 任务二粘贴块：云端并行沙箱 worktree MVP

```text
背景：同一个 monorepo（IHUI-INF-AI/IHUI-AI，pnpm workspace）。目标是在这台服务器上做「云端并行沙箱
worktree」MVP：每个任务拉起一个隔离容器 + 独立 git worktree，跑代码任务/agent，结束后回收结果并销毁。
代码侧基础已就绪：agent-runtime 会话已 PG 持久化（表 agent_runtime_sessions，write-through + 惰性恢复 +
SessionManager.adopt()），跨机恢复会话可用；apps/api = Fastify5 + Drizzle + PostgreSQL，
apps/ai-service = FastAPI + LangGraph。仓库内已有 detached worktree 并行协作纪律可参照。

第一步 盘点（只读）：
- 服务器 Docker/podman 版本、磁盘余量（沙箱需要 ≥20GB）、CPU/内存上限；
- 仓库内是否已有 sandbox/沙箱相关代码（grep sandbox / worktree 相关路由与 service），有则在其上迭代，
  不要重复造轮子；apps/api 的 admin 路由鉴权模式（authenticate + requireActiveUser + roleId）先读懂。

第二步 基础镜像：
- 构建沙箱基础镜像：node22 + pnpm + python3.13 + git + 常用构建工具，pnpm store 做成缓存层
  （冷启动快）；镜像内预置 monorepo 依赖安装缓存，不含任何生产密钥。

第三步 沙箱生命周期（MVP 核心）：
- 创建：git worktree add /srv/sandboxes/<id> <ref> → docker run 挂载该目录
  （其余宿主路径一律不挂载；资源限额 cpu/memory/pids；网络默认仅出站）；
- 执行：容器内非 root 用户跑 `pnpm install --frozen-lockfile` + 任务命令（任务命令白名单：
  typecheck / test / lint / 由 prompt 驱动的 agent-runtime 执行）；
- 回收：抓取 diff、exit code、关键日志 → 归档 → worktree remove + 容器销毁（含 --force 清理）；
- 并发与队列：同 host 并发上限 3，超出排队；全局超时（默认 30 分钟，最大 60）到点强杀并清理。

第四步 API（apps/api 内新增，鉴权沿用 admin preHandler 模式）：
- POST /api/admin/sandbox：body {ref, taskType, prompt?, timeoutMinutes?}，创建并返回 sandboxId；
- GET /api/admin/sandbox/:id：状态 + 日志尾部 + diff/exit code（完成后）；
- DELETE /api/admin/sandbox/:id：终止并强制清理；
- zod 校验：ref 只允许 main 与已存在 tag/commit sha；prompt ≤ 8000 字符；timeoutMinutes ≤ 60。

第五步 安全自证（必须实测并在报告中给出证据）：
- 容器内无法访问生产 .env / 数据库凭据 / docker.sock / 宿主其他目录；
- 容器以非 root 运行；无法对外扫描内网（按需加网络策略）；
- 强杀超时任务后无容器/worktree 残留（写一个清理兜底脚本 + cron 兜底扫残留）。

验收（全部满足才算完成）：
1. 从 main 拉 worktree 跑一次 typecheck 类任务，成功返回 diff + exit code + 日志；
2. 并发 3 个任务互不干扰（目录隔离、端口不冲突）；
3. 超时任务被强杀且资源零残留（含兜底 cron 验证）；
4. 第五步安全自证四条全部有实测证据；
5. 产出《沙箱 MVP 验收报告》：curl 使用示例、镜像构建时长、冷启动耗时、并发上限依据、遗留风险。

红线：与部署任务相同（禁 force push / 禁动 WIP / 可用性优先）；沙箱目录必须独立于生产部署目录；
销毁前日志先归档；禁止在生产数据库建实验表——确需建表先回报方案再动手；沙箱环境永不持有生产密钥。
```

## 两个任务的先后依赖

- 部署管道（任务一）先行：它同时会完成 nginx /v1 /ws 同步、tauri.localhost CORS、生产 web 更新——这些都是线上可用的前提。
- 沙箱（任务二）依赖部署稳定后再上，避免部署调试与沙箱实验互相干扰。
- 服务器 agent 交回验收报告后，把报告发回给我，我来做代码侧对齐（如沙箱 API 的 api-client/web 端接入）与三仓同步。
